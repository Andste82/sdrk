# Backends

A backend implements kernel traits of `sdrk-core` for the variants it accelerates. The facade `sdrk` picks, per kernel and sample type, the implementation that runs ([kernels.md](kernels.md)); `sdrk::backend_for(kernel, sample_type)` reports its name (`"simd"`, `"fallback"` or `"chained"`). Backends depend only on `sdrk-core` and `sdrk-device`, never on each other.

Today there is one backend, `sdrk-backend-simd` (layer `crates/backends`, `no_std`, no heap). The embedded backends come in later milestones.

## `sdrk-backend-simd`

`pub struct Simd;` implements the kernel traits for the variants of the table below. Everything else (the other kernels, formats and filter shapes the vector code does not cover) is delegated by the backend itself to `sdrk_core::Fallback`, so a call that the vector path cannot take returns exactly the result and the errors of the fallback.

The vector code is written once against the `Simd` trait of [`fearless_simd`](https://crates.io/crates/fearless_simd) 1.1.0 (pinned). Where the portable operations are not enough, a kernel may add a path for one level with the intrinsics of `core::arch` (decision D1 of the SIMD optimization): a function declared with `fearless_simd::kernel!` for the token of its level, so the intrinsics are safe to call with the level fixed at compile time or detected at run time; `unsafe` only for small helpers the safe intrinsics cannot express (pointer and interleaving loads and stores, masked loads, gathers) in a module per architecture, with `// SAFETY:` on every block; the generic code stays as the fallback of every such path, and a test compares the two at every level (natively, under Intel SDE, QEMU and wasmtime). The module documentation of `src/level.rs` gives the rules and an example. Its levels:

| Target | Levels |
| --- | --- |
| x86-64 | `sse2` (baseline), `sse4.2` (`x86-64-v2`), `avx2` with FMA (`x86-64-v3`), `avx512` (Ice Lake class: `avx512f`, `bw`, `dq`, `vl`, ...) |
| AArch64 | `neon` |
| wasm32 | `simd128` (compile-time only; without the target feature the level is `scalar`, the generic code); with the cargo feature `relaxed-simd` and the target feature `+relaxed-simd` also relaxed SIMD, see below |
| anything else (32-bit x86, Cortex-M, RISC-V, ...) | none; the facade uses `Fallback` and does not build the backend |

### Dispatch

- **Without the feature `std`** the level is fixed at compile time by the target features: `-C target-cpu=x86-64-v2` gives SSE4.2, `-C target-cpu=x86-64-v3` AVX2, `-C target-cpu=sapphirerapids` AVX-512, the default build SSE2. No detection code runs.
- **With the feature `std`** (enabled by the facade's `std`, which `sdrk-pipeline`, the examples and the testkit's `std` feature turn on) every kernel entry asks `fearless_simd::Level::new()` for the level of the running CPU. The answer is cached by the standard library inside `fearless_simd`, so it is not global state of SDRk; the per-call cost is one load and one branch. The instruction counts show it: the levels `avx2` (fixed at compile time) and `avx2-runtime` (detected at run time) differ by at most 2 % for every accelerated kernel but `fft` `C32` at N = 64 (7 %, 6.28 against 5.84 instructions per sample: about 28 instructions more per call, 18 of them in `level::dispatch_fn!`; open item M13-9, [performance.md](performance.md)).
- `--cfg sdrk_fallback_only` (set through `RUSTFLAGS`, **not** a cargo feature, because `cargo test --all-features` would switch a feature on and silently disable the backend) makes the facade use the fallback everywhere. `sdrk::SIMD_BACKEND` tells whether the accelerated kernels run on the backend in this build.
- The facade feature `simd` (default) can be switched off to drop the backend.

`sdrk_backend_simd::level_name()` returns the name of the level the kernels run at.

### Kernels and their contract

"Bit-exact" means the output equals the output of `Fallback` bit for bit; "tolerance" means the minimum SNR of `docs/kernels.md` against the f64 reference. Block-size invariance holds for all of them but the `f32`/`C32` recursions `deemphasis`, `dc_block` and `dc_block_real`: an output sample depends only on its window and the state, whatever the block boundaries (the tests compare random chunk plans bit for bit). The recursions round their state to `f32` at every call boundary; their chunk plans are checked against the regression guards of the golden cases instead (maintainer decision of 2026-10-29, [kernels.md](kernels.md#backends-and-the-numeric-contract)).

`stereo_pll` (`f32`, `Q15`) stays with the fallback by decision of M24 (D110): the phase of every sample depends on the detector output of the previous one, and the loop is bit-exact, so a block scan with another result is not allowed; `backend_for` reports `fallback`. It is counted against liquid-dsp's `nco_crcf` loop (`f32`) and as `info` (`Q15`), [performance.md](performance.md).

`squelch` (`C32`, `CQ15`) stays with the fallback by decision of M19: the average power is a first-order recursion (one multiply-add per sample on the previous value) and the gate decision depends on it, so it cannot be vectorized without changing its result; only the cheap `|x|^2` could be, which would not pay for the extra pass. The loop is bound by the latency of that recursion, not by throughput: the `C32` chain is the subtraction, the multiplication and the addition of the contract (9 cycles on Zen 3), and the fallback keeps everything else off it (one loop per gate state, left through predicted branches; see `fallback/squelch.rs`), so at `avx2` it needs 21.25 instructions in 10.70 simulated cycles per sample on `znver3`, with a port bound of 5.0. A SIMD pass for `|x|^2` and the output would lower only the port bound. The `CQ15` chain is a shift, a multiplication and an addition (the average is carried as `p + 2^30`, split into its high and low 31 bits); its port bound is close to its latency, so a separate pass would add more than it saves. The `C32` variant is counted against GNU Radio's `pwr_squelch_cc` loop, the `CQ15` variant as `info` against the fallback (`benches/limits.json`, [performance.md](performance.md)); `backend_for` reports `fallback`.

`biquad` and `biquad_real` (all four types) are accelerated with the wavefront of D18: M22 kept `biquad_real` with the fallback because every output depends on the previous output of the same section; the sections are in series, but section `k + 1` only needs the output of section `k` from one sample before, so two sections fill the lanes of one vector one sample apart. The two-lane path of M22 (re and im in two lanes, section by section) and its 25 % rule are replaced (open item M22-4 is closed); AVX-512 runs the same path as the other levels. The counts against KFR, CMSIS-DSP and the fallback (D15, D16) are in [performance.md](performance.md); `backend_for` reports `simd` for all four.

`agc` `CQ15` stays with the fallback by decision of M20: the gain of every sample depends on the output of the previous one (the gain is updated after each sample from the measured amplitude), a per-sample feedback that cannot be vectorized without changing its result. The `C32` `agc` is accelerated since the review of M20 (open item M20-6) around the same recursion: the magnitudes `|x|` and the output products do not depend on the gain, so the backend computes them in vectors per block and runs the scalar recursion (`gains_with`, the update of the fallback) in between (row above); the output level is `g |x|`, which the fallback computes the same way, so the values are equal bit for bit. `deemphasis`, `dc_block` and `dc_block_real` (`f32`, `Q15`, `C32`, `CQ15`) are first-order recursions on the previous output and stay with the fallback: a block formulation (a prefix scan over a vector) would be several times faster but changes the roundings, and the facade shares the bits of the fallback (suite cases `*_vs_reference`). The fallback has two forms of each recursion with the same bits: the loop of the contract, and a form with a shorter chain from one output to the next (the `f32` flush decided beside the arithmetic: the comparison of the unflushed value selects the product `r y` or 0, or the step from the value or from 0; the Q15 input terms and rounding constant added in `i32` before the product). The short form costs instructions, so each kernel uses it only on the targets where it simulated faster on both core models of every level (constants `SHORT_*` in `sdrk-core/src/fallback/demod.rs`, with the numbers); the embedded targets run the contract loop. `deemphasis`, `dc_block`, `dc_block_real` and the `CQ15` `agc` are counted as `info` against the fallback at every level (no established scalar library is linked for the recursions yet; candidates are the loops of GNU Radio, `fm_deemph` with `iir_filter_ffd` and `dc_blocker`, whose `dc_blocker` is a different algorithm, moving averages); the `C32` `agc` is counted against the `agc_cc` loop of GNU Radio (`benches/refs/gr-agc.c`, [performance.md](performance.md)). `backend_for` reports the backend for the `C32` `agc` and `fallback` for the others. `am_demod` profits from the accelerated `mag`.

**Halfband kernels (`halfband_decimate`, `halfband_decimate_real`, `real_to_complex`).** A filter of `N = 2 m + 1` taps (`m` odd) has non-zero taps at the even indices `2 i` (`i = 0 ..= m`) and at the centre. With the decimation by 2 and the history of `N - 1 = 2 m` samples, the even-index taps of every output read one parity of the virtual stream `history ++ input` (the even stream `s[j] = v(first + 2 j)`), the centre tap the other parity (`o[t] = v(first + m + 2 t)`), so `y[t] = sum_i h[2 i] s[t + m - i] + h[m] o[t]`: a plain FIR over the even stream in which consecutive outputs read consecutive samples.

- Blocks of 64 outputs gather `s` and `o` into scratch arrays on the stack (the components of a complex sample stay interleaved, so the results are stored to the output as they are; the history and the end of the input need no second code path; the copy of a sample is one move of a constant width), then compute lanes of consecutive output values in the transposed form (no horizontal sums; the sample `p` places on is `C p` values on, `C` = 1 or 2). A filter of up to 1023 taps fits the scratch; longer ones run on the fallback, and nothing of the state has been touched then.
- `f32` values: eight vectors of outputs at a time (then four, then one at the end of a block), a broadcast coefficient times the pre-added pair `s[t + m - i] + s[t + i]` (the taps are symmetric, decision D71, checked per call, else the fallback runs), FMA on AVX2, AVX-512 and NEON (D5), the vector width of the level (4, 8, 16 lanes). The result is within the 110 dB contract and does not depend on the block boundaries (every output goes through the same sequence of operations whatever its lane); the pre-add overflows to infinity for samples above about `1.7e38` where the fallback's sum does not.
- `Q15` values: exact `i16 x i16` products summed in `i32` in groups of 16 outputs written for the compiler's vectorizer (the code of every level is the same generic loop, compiled with the target features of the level), then `(sum + 2^14) >> 15` clamped to the `i16` range, which is `Acc64::finish`. `i32` suffices because the filter is only accepted if the sum of the absolute taps is at most 65535 raw (twice full scale): the sum of the products then stays below `2^31 - 2^14` for every input including `-32768`; other filters run on the fallback. Bit-identical with the fallback for every input.
- `real_to_complex` gathers the even stream with the sign of `(-j)^n` applied to the samples (`-x` where `n mod 4 = 2`, the saturating negation for `Q15`; the signs are not folded into the taps) and the centre stream from the imaginary parts (`-x` at `n mod 4 = 1`); a history sample is read as its real part at the even stream and its imaginary part at the centre stream, as in the fallback. The history stores the shifted samples `u` exactly as the fallback does.

**Dot products (`fir` family).** Every output is the dot product of the taps with a window of the virtual stream `history ++ input`.

- `C32` `fir` and `fir_decimate` compute several outputs at a time with the taps of a block of 128 taps (a longer filter adds the partial products of its blocks in the output).
- Consecutive outputs (`fir`, and `fir_decimate` by 1) use the transposed form: a vector holds `L/2` consecutive outputs, and every broadcast tap multiplies the samples at its offset for 4 to 14 vectors at a time, so there is no horizontal sum. The products of a block of 8 taps form one chain (two interleaved chains at SSE2/SSE4.2), which is added to the output's total. On x86 the vectors of a pass are 8 samples apart, so the loads of different taps stay separate memory operands.
- Decimation uses the chunk form: the dot product of 6 to 8 windows at a time with the taps in chunks of half a vector of complex samples, in unrolled groups of 8 chunks summed in one chain per group. The samples of the partial last chunk beyond the window are cleared by a mask, so a non-finite neighbour does not leak in. The complex lanes are added by halving.
- Real samples (`fir_interpolate_real`, `resample_real` `f32`) run the same two forms with one component per sample: a vector of the transposed form holds as many consecutive outputs as it has lanes (its vectors are a whole vector apart, 8 samples at AVX2 and SSE2/SSE4.2, 16 at AVX-512, 4 on NEON and SIMD128; AVX-512 runs 12 vectors per pass, so that a pass of 192 outputs fits the scratch window of a run), and the chunk form computes 8 windows at a time (AVX-512 runs it on 8-lane vectors, which simulated faster than 16 lanes), whose lanes are added by halving down to four and then four outputs at a time share the last two steps (two pairwise sums and one `unzip`), so every output gets the same sum whatever its neighbours.
- Runs whose windows lie in the input read it in place. The windows that reach into the history or past the end of the input are copied into a scratch window of 192 samples and computed in the same way, so an output is bit-identical whichever way the input was split.
- The levels with FMA (AVX2, AVX-512, NEON) fuse the multiply-adds (decision D5).
- `C32` `fir_interpolate` and `resample`: the outputs `r, r + L, r + 2L, ...` of a call have the phase of output `r`, and their windows are `M` samples apart (the closed form of the phase counter gives where each progression starts). Each progression is one contiguous filter with the taps `h[p + L i]` of its branch, step `M` and output stride `L`: the transposed form for `fir_interpolate` (`M = 1`), the chunk form otherwise. The outputs of a run are computed into the scratch window and then spread over the output with stride `L` (a pointer step per output, so the stores do not form a chain of bound checks).
- `CQ15` `fir`/`fir_decimate` and the polyphase kernels (and `Q15` `fir_interpolate_real`/`resample_real`) still compute one output at a time with taps prepared once per call, reversed and duplicated per lane (once per lane for `Q15`). A partial chunk inside one slice is read in place with a mask; a window that straddles the history and the input is assembled with two copies. Where the grouped fallback engine is faster on both core models of a level (all six at `sse2`; all but `resample_real` at `avx2`; `fir`, `fir_interpolate` and `fir_interpolate_real` at `avx512`; `fir_interpolate_real` at `simd128` by instructions), the kernel runs the fallback instead, bit-identical, from one table in `fir.rs` (`runs_fallback`, decision D65) and only in a build compiled for that level.

**FFT.** `C32`: a decimation-in-time transform in place without a separate bit-reversal pass (module documentation of `src/fft/c32.rs`). Between the passes the data is in blocks of `L` complex numbers (`L` the `f32` lanes of a vector) stored as `L` real parts followed by `L` imaginary parts.

- The first pass does the bit reversal, the first `log2 L` stages and the conversion to that split form in one pass over `L x L` tiles: a tile is loaded row by row, transformed across its rows, transposed, and stored in place of its mirror tile (and the mirror in its place).
- Radix-4 passes with three complex products per butterfly follow. If the number of remaining stages is odd, the radix-2 stage and the first radix-4 pass are one pass over groups of eight blocks (the same operations as the two passes, bit for bit, without storing and loading the data in between; AVX2, N = 1024: 10.33 to 9.82 instructions and 2.86 to 2.74 / 2.61 to 2.48 simulated cycles per sample on znver3 / alderlake). Where the eight inputs of a radix-8 butterfly and its twiddles fit the registers (NEON with 32 registers, wasm32), radix-8 passes take the stages that remain after as few radix-4 passes as make their number a multiple of 3.
- The last pass stores interleaved samples (and scales the inverse transform by `1/N`).
- For `N = L^2` (16 with 4 lanes, 64 with 8) the tile is the whole transform: a codelet multiplies the transposed tile by its twiddles and runs the remaining `L`-point DFT across the rows in registers; the 8-point second DFT of the `N = L^2` codelet stores its two halves one after the other.
- Twiddles: with the feature `fft-tables` the passes of spans up to 4096 read static per-span tables in split form (`build.rs`), bit-identical with the plan's twiddles for power-of-two sizes (`W^3k` exact instead of a product); the plan's table serves only the spans above 4096. Without the feature every twiddle comes from the plan: contiguous loads where the table stride is 1, scalar loads otherwise, and products of two exact entries for the rest. The caveat for plans from `FftPlan::from_twiddles` is in [kernels.md](kernels.md).
- Levels: AVX2 deinterleaves the rows of a tile with one `vshufps` per vector and transposes with in-lane shuffles (24 per 8 x 8 matrix instead of 48); its blocks keep the lane order of those shuffles (0, 1, 4, 5, 2, 3, 6, 7) through all passes, with the twiddles in the same order (a second copy of the span tables in that order on x86-64, the plan's twiddles deinterleaved with `vshufps`), so the last pass stores with `vunpcklps`/`vunpckhps` only, without the two lane permutations per block of the natural order; bit for bit the same result (whole-loop simulated cycles per sample on znver3 / alderlake: N = 1024 2.55 / 2.39 to 2.35 / 2.26, N = 4096 2.81 / 2.65 to 2.60 / 2.52); NEON moves interleaved rows with `ld2`/`st2`; AVX-512 uses the portable operations with 16 lanes from 256 points and 8 lanes below. The sizes 16 to 256 get a transform of their own in which the size is a constant.

`CQ15`: see the table; the module documentation of `src/fft/q15.rs` has the details. The x86 radix-4 constants pass through `core::hint::black_box` to keep the `pshufb` patterns and splats in registers in the run-time-detection build; this is a best-effort hint whose effect (`avx2-runtime` 1.001 times `avx2`) may change with the compiler.

**FMA.** Used by the tolerance kernels on levels that have it: `rotate` `C32` (in the `f32` loop and in the `f64` polynomial and products of the per-call setup), the `C32` FFT, `fir`, `fir_decimate`, `fir_interpolate` and `resample` `C32` and `fir_interpolate_real` and `resample_real` `f32` (the polyphase branches run in the forms of `fir` and `fir_decimate`), `halfband_decimate` `C32`, `halfband_decimate_real` `f32` and `real_to_complex` `C32`, and `dot` `C32` and `dot_real` `f32` on AVX2, AVX-512 and NEON (D5); never in a bit-exact kernel. `quad_demod` and the post-processing of `rfft` use separate multiplications and additions on every level. Because FMA and the vector width change the roundings, the tolerance kernels give different bits on different levels (and differ from the fallback); the contract bounds the difference.

### Level-specific paths (D1)

The kernels with `core::arch` paths, each with the generic code as its fallback and a test against it (the `unsafe` helpers sit in the per-architecture module of the file, with `// SAFETY:` on every block):

- `convert.rs`, `convert_out.rs`: a path per level (x86, NEON, SIMD128); the `unsafe` of `convert_out` is limited to the AVX-512 masked load and store.
- `mix.rs` (`rotate`): `x86::InLane` (AVX2 and AVX-512 in-lane shuffles, safe intrinsics in `kernel!`) and `neon::Ld2` (`vld2q`/`vst2q`). Both are bit-identical with the portable split; the unit test in `mix.rs` covers calls of up to 5000 samples.
- `demod.rs` (`quad_demod`): x86 `discriminate_avx2` / `discriminate_sse4_2` (safe intrinsics) and AArch64 `discriminate_neon` (one `unsafe` `vld2q_f32`), each with a bit-exact unit test against the portable loop; `CQ15` is tested against the fallback (at most 1 LSB, every tail up to 72 samples, full-scale corners) and for block invariance.
- `agc.rs` (`agc` `C32`): the generic loops for the magnitudes and the products on every level; on AArch64 the minimum and maximum of the recursion as `fminnm`/`fmaxnm` in `asm!` (the only `unsafe`): `f32::min` adds a canonicalising `fminnm` of every operand that comes from another basic block, and with the intrinsics `vminnm_f32` the compiler evaluates every branch of the step and selects, about twice the instructions of the branch taken; it does not move an `asm!` block out of its branch. The test `tests/agc.rs` compares it with the fallback.
- `biquad.rs` (`biquad` `C32` and `CQ15`, `biquad_real` `f32` and `Q15`): generic code on every level for `f32` and `C32`; the `Q15` and `CQ15` pairs run in integer lanes on x86 from SSE4.1 and on NEON (the module `int`: one generic step over the trait `Lanes`, whose implementations wrap the intrinsics of the level in `fearless_simd::kernel!` functions, and an empty `asm!` block per step that keeps a partial sum apart), in `f64` lanes elsewhere (the levels differ in the rounding there, a vector floor where the level has one). The unit test of the module runs every integer path the host has (`Two` of SSE4.2 also on an AVX2 host) against the fallback. The four entries go through `dispatch_fn!`, and the hot loops call methods, not closures: with the level detected at run time a closure is not compiled with the target features of the level and kept the state of the `Q15` sections in memory (1.32 against the static AVX2 build before, 1.00 after). The test `tests/biquad.rs` compares all four with the fallback (all lengths, offsets, one to five sections, unstable coefficients, NaN, infinities, signed zeros, subnormals, random chunks with `reset` and `set_coefs`, and the rounding ties and saturation of one tap for every `b0` as the single section and in both sections of a pair).
- `spectrum.rs` (`mag_sq`, `mag`), `table.rs` and `modulate.rs` (`fm_mod`, the NCO lookups of `rotate` `CQ15`), `mix.rs` (`rotate` `CQ15`: `x86_q15`, `neon_q15`, `wasm_q15`, with `unsafe` only for the store and the scalar loads of the entry offsets, the entry loads and `ld2`/`st2`), `fft/c32.rs` and `fft/q15.rs`: paths per level as described above.
- `dot.rs` (`dot` `CQ15`, `dot_real` `Q15`): paths for SSE2, SSE4.2, AVX2, AVX-512 (`dot` only; `dot_real` runs the AVX2 path there), NEON (`dot_real` only) and SIMD128 with safe intrinsics, tested bit for bit against the fallback at every length up to 1100 and around the flushes of the 32-bit sums (`tests/dot.rs`); `scale.rs` (`scale` `CQ15`): paths for SSE4.2, AVX2, AVX-512, NEON and SIMD128 (`tests/scale.rs`).
- `fft/real.rs` (`rfft`): the reversed loads and stores of the post-processing with `shufps`/`unpck*ps` at SSE2 and SSE4.2 (safe intrinsics), with a bit-exact unit test of the bins of each level against the scalar formula.

Helpers called from a level path must be `#[inline(always)]` functions or local macros. Closures may be defined inside the body of the `kernel!` function, which they inherit the target features of, but must not be passed to generic functions compiled outside it: such a function, and the closure it calls when it is not inlined, is compiled without the level's target features when the level is detected at run time, and then runs without the vector instructions (seen in `rotate`: 2.85 instead of 2.39 instructions per sample at `avx2-runtime`, where the closures were handed to generic helpers). The one exception is the `C32` FFT in builds with debug assertions (below).

### Cargo features of the backend

- `fft-tables`: the static per-span twiddle tables of the `C32` FFT, 41 KiB of read-only data (41 904 bytes); on x86-64 another 40 832 bytes for the copy of the tables of the spans 16 to 4096 in the lane order of the AVX2 passes (82 736 bytes in all). The facade enables it through a target-specific dependency on x86-64 and AArch64 only, and offers the facade feature `fft-tables` for wasm32 (decision D13). wasm32 measured both ways: 35.5 / 58.6 / 67.6 fuel per sample at N = 64 / 1024 / 4096 without the tables, 31.0 / 53.1 / 61.8 with them (and a slightly higher SNR).
- `nco-tables`: the static NCO interpolation tables of `fm_mod` and `rotate` `CQ15`, 96 KiB of read-only data. The facade enables it by default on x86-64 and AArch64 through a target-specific dependency and offers the facade feature `nco-tables` elsewhere. `fm_mod` on wasm32: 34.78 fuel per sample without, 27.77 with the tables.
- `relaxed-simd`: see below.

**Builds with debug assertions.** The helpers of the `C32` FFT are `#[inline(always)]` only without debug assertions. A downstream crate in the dev profile (opt-level 0) gets frames of at most about 10 KiB instead of megabytes, and builds in seconds. Each such helper is compiled without its level's target features there (correct, but slower).

**Run-time detection and code size.** With the feature `std` on x86 the sized `C32` transforms dispatch through `level::dispatch_fn!`: one `fearless_simd::kernel!` function per level (AVX-512, AVX2, SSE4.2) that takes the arguments in registers instead of a closure captured by reference, and the levels below SSE4.2 out of line, so that the dispatching function stays small. With the level fixed at compile time `dispatch_fn!` is `dispatch!`. The run-time-detected build carries every level of the FFT: about 300 KB of `.text` (5 sized instances for 4 x86 levels and 2 directions).

### Relaxed SIMD (wasm32)

The cargo feature `relaxed-simd` of `sdrk-backend-simd` (forwarded by the facade `sdrk` and by `sdrk-wasm`) is for builds with `RUSTFLAGS="-C target-feature=+simd128,+relaxed-simd"`. In such a build the `C32` variants of `fir`, `fir_decimate` and `fir_interpolate` (`resample`) and the `f32` variants of `fir_interpolate_real` (`resample_real`) accumulate with the relaxed multiply-add (`f32x4.relaxed_madd`), and `rotate` and the `C32` FFT, which use `mul_add` on every level, get it from `fearless_simd` (it uses the relaxed instruction for `mul_add` whenever the target feature is on). `mag_sq` uses no multiply-add, so it stays bit-exact in the relaxed build too. The engine may fuse the multiplication and the addition or not, whichever is faster on its hardware: the results are **not bit-exact** and differ between hosts, but stay within the contracts of the table (the tolerance kernels). On every other target, and on wasm32 without the target feature, the feature changes nothing. The block-size invariance of the `fir` family holds in the relaxed build as well, because every path through the window uses the same instruction.

`cargo xtask wasm-pkg --relaxed` builds this variant as `sdrk_relaxed.wasm`; it is never selected automatically ([wasm.md](wasm.md)). The CI job `test_wasm32` runs the tests of the backend, the facade and the blocks with it under wasmtime.

### Limits of the vector paths

- `convert`, `convert_out`: only the formats named above.
- `CQ15` filters longer than 256 taps, `CQ15` polyphase filters whose branches do not fit 384 prepared samples and `Q15` real polyphase filters whose branches do not fit 768 run on the fallback (the result is the same, only slower).
- `fm_mod`: if a phase step does not fit 2^51 (a deviation of 10^15 Hz and more) or the input is NaN, the rest of the call runs on the fallback.
- The FFT sizes are those of the plan (16 to 65536). The `CQ15` FFT runs sizes below `max(V^2, 4V, 64)` samples (x86, wasm32) with the generic radix-2 code; NEON has no such limit.

## How to add a backend

1. A crate `crates/backends/sdrk-backend-<name>` that depends on `sdrk-core` (and `sdrk-device`), `#![no_std]`, implementing the traits for the variants it accelerates with `pub struct <Name>;`.
2. In the facade: `impl BackendName for <Name>` with the name, and the entries of `crates/facade/sdrk/src/delegations.rs` for the accelerated kernels (`=> <Name>`, guarded by `#[cfg(...)]`).
3. Cases `backend_vs_fallback_*` of the suite apply to the facade, so they exercise the backend automatically; add the platform to `cargo xtask count` and the CI matrix.
4. Unsafe code: only in a separate module per architecture with `#[allow(unsafe_code)]` locally, `// SAFETY:` on every block (enforced by `clippy::undocumented_unsafe_blocks`) and a line in the decisions log.
