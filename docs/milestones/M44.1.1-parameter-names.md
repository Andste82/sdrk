# M44.1.1 — One name per parameter: no mapping in the composite blocks

> Plan: [PLAN.md › Phase 10](../PLAN.md#phase-10--digital-modes) · Depends on: [M44.1](M44.1-qam-building-blocks.md) · Next: [M44.2](M44.2-qam-any-order.md)

> **Status: draft** (2026-11-17), written from a design discussion with the maintainer. Not yet reviewed. Values marked *(to be confirmed)* are first estimates and are fixed by the implementation through the decisions log.

## Goal

A parameter that means the same thing has the same name and the same values in every block, and a composite block forwards its parameters to its building blocks unchanged, so that no composite needs code that maps or converts a parameter:

- **`constellation` instead of `order`** in `qam_mod`, `qam_demod`, `qam_frame_encode`, `qam_frame_decode`, `psk_mod` and `psk_demod`, with the values of `symbol_map`, `symbol_demap`, `costas` and `equalize` (`bpsk`, `qpsk`, `8psk`, `qam16`, `qam64`).
- **The pulse filter as building blocks:** `pulse_shape` (transmit) and `pulse_match` (receive) hold `rolloff`, `span` and the symbol timing and design their root-raised-cosine taps themselves. The composites no longer compute taps.
- **Every composite forwards through `ParamMap`:** each public parameter of `qam_mod`, `psk_mod`, `qam_demod`, `qam_frame_encode` and `qam_frame_decode` appears once and goes, with the same value, to every building block that has it.

## Why

- The maintainer's rule (2026-11-17): the same name for the same thing. Today `qam_mod` says `order` 16 where its building block `symbol_map` says `constellation` `qam16`, and the composite converts one into the other. `costas` already made this change in M44 (D1205: `constellation` replaced the `order` 2, 4, 8 of M40).
- `rolloff` and `span` are parameters of the pulse filter, but no building block has them: each composite designs the taps and hands them to `interpolate` (`InterpolateBlock::with_taps`) or `fir`. With the pulse filter as a building block, the design exists once and the parameters are forwarded like every other.
- Without conversions every composite answers `param` and `set_param` through its `ParamMap`, the tool of M31. This closes I44.1-5 (1) (D1553).

## Order

M44.1.1 starts when M44.1 (PR #165) is merged and comes before M44.2, which then adds the QAM constellations `qam256` and `qam1024` under the names of this milestone. Merging `psk_*` and `qam_*` into one modulator and one demodulator is noted in the backlog and is not part of it.

### R2 — Layers and dependencies

The folder of a crate is its layer. A crate may depend only on crates in **lower** layers (or, for the testkit, on any library layer). `cargo xtask check` enforces this by reading `cargo metadata` and the crate paths.

| Layer (folder) | Crates | May depend on (workspace crates) | `no_std`, no heap |
| --- | --- | --- | --- |
| `crates/core` (lowest) | `sdrk-device` | — | yes |
| `crates/core` | `sdrk-core` | `sdrk-device` | yes |
| `crates/backends` | `sdrk-backend-*` | `sdrk-core`, `sdrk-device` | yes |
| `crates/facade` | `sdrk` | core, backends | yes |
| `crates/proto` | `sdrk-proto` | `sdrk-device` | yes |
| `crates/blocks` | `sdrk-blocks` | facade, core, proto | yes |
| `crates/pipeline` | `sdrk-pipeline` | blocks, proto, facade, core | no (std/alloc allowed) |
| `crates/io` | `sdrk-io` | core (types only) | no |
| `crates/testing` | `sdrk-testkit` | any library crate above | `no_std` by default; feature `std` adds file I/O and proptest helpers |
| `bindings/*`, `examples/*`, `targets/*`, `benches/*`, `xtask` | — | anything | no |

Additional rules:
- Within `crates/core` the rank is by crate name: `sdrk-device` (rank 0) < `sdrk-core` (rank 1); `sdrk-core → sdrk-device` is allowed, the reverse is not. All other layers are one rank per folder.
- Backends never depend on each other. Only the facade `sdrk` knows the backends.
- `sdrk-proto` (from M37 on) holds protocol logic without signal processing (bit and byte framing, checksums, packet types); it depends on `sdrk-device` only, and nothing below `crates/blocks` depends on it.
- Only `sdrk-testkit` and test code use the `reference` feature of `sdrk-core`.
- External crates allowed in heap-free crates: `num-complex` (default-features = false, features = ["bytemuck"]), `libm`, `bytemuck`, `heapless`, `fearless_simd` (backends only). Anything else needs a line in `docs/decisions-log.md` and must pass `cargo deny`.

### R3 — `no_std` and no heap (applies to every crate marked "yes" above)

1. The crate root starts with `#![no_std]`. The crate never writes `extern crate alloc;` and never uses `Vec`, `Box`, `String`, `Rc`, `Arc`, `BTreeMap` or anything else that allocates. `cargo xtask bare-metal` builds these crates for `thumbv7em-none-eabihf`, which has no global allocator, so any accidental allocation fails the build.
2. Memory is provided by the caller. State types are generic over their storage: a field that holds samples has a type parameter `S: AsRef<[T]> + AsMut<[T]>` (read-only data: `S: AsRef<[T]>`). On a microcontroller the caller passes `[T; N]` or `&mut [T]`; in upper layers the caller may pass `Vec<T>`. Constructors validate lengths and return `Err`, never panic.
3. Fixed-capacity containers come from `heapless` when needed.
4. No function may keep more than 4 KiB on its stack (WASM and MCU stacks are small). Large buffers belong in caller-provided storage. `clippy.toml` sets `stack-size-threshold = 4096` and the workspace enables `clippy::large_stack_frames` and `clippy::large_stack_arrays` as errors.
5. Math functions come from `libm` (e.g. `libm::sinf`, `libm::atan2f`, `libm::log10f`), never from `f32::sin()` & co. This keeps code `no_std` **and** makes results identical on every platform because `libm` is pure Rust.
6. Upper layers (`pipeline`, `io`, `bindings`, `examples`, `xtask`, testkit feature `std`) may use `std` and allocate. The only `std` use allowed below the heap boundary besides the testkit's `std` feature is runtime CPU-feature detection in backend crates behind their `std` feature (M13); it never allocates. The pipeline allocates only while *building*; after `build()` returns, processing must not allocate (tested with a counting global allocator in M10).

### R4 — Clean interfaces

1. Each crate exposes a small, documented public API through `lib.rs` re-exports; everything else is `pub(crate)`. Module layout inside a crate is an implementation detail.
2. Public enums that may grow are `#[non_exhaustive]`. Public structs with invariants have private fields, a validating constructor (`new(...) -> Result<Self>`) and getters.
3. Kernels follow the **one trait per kernel** pattern defined in M02: the trait is generic over the sample type, `Fallback` (in `sdrk-core`) implements it for every supported sample type, `Reference` (feature `reference`) implements it as the f64/integer specification, backends implement only the variants they accelerate, and the facade type `sdrk::Sdrk` implements all of them by delegating to the chosen implementation.
4. Kernel calls never allocate, never block, never read a clock, never use randomness, and never print.
5. Every public item has a rustdoc comment; every public function with non-trivial behaviour has a doc example that compiles (`#![deny(missing_docs)]` in every library crate; `cargo test --doc` runs the examples).
6. All public types are `Send`; state types and blocks are also `Sync` unless they need interior mutability (they should not). Add compile-time assertions in each crate's tests: `fn _assert_send<T: Send>() {}` called for every public type.

### R5 — One error-handling scheme for the whole workspace

1. The lowest crate `sdrk-device` defines the shared classification:
   ```rust
   #[derive(Debug, Clone, Copy, PartialEq, Eq, Hash)]
   #[non_exhaustive]
   pub enum ErrorKind {
       InvalidArgument, LengthMismatch, BufferTooSmall, OutOfRange, Unsupported,
       CapacityExceeded, InvalidState, ResourceLimit, Parse, Validation,
       Io, Device, Timeout, Disconnected, Internal,
   }
   pub trait SdrkError: core::error::Error {
       fn kind(&self) -> ErrorKind;
   }
   ```
2. Every library crate defines **its own** `pub enum Error` (`#[non_exhaustive]`, `Debug`, `Clone`, `PartialEq`) and `pub type Result<T, E = Error> = core::result::Result<T, E>;`. The enum implements `core::fmt::Display` (lowercase message, no trailing period), `core::error::Error` and `SdrkError`. Heap-free crates keep their error variants allocation-free (`&'static str` and integers only). Upper crates may carry `String` paths (e.g. `nodes.ddc.params.frequency_hz`).
3. Wrapping: an upper crate's error has a variant like `Core(sdrk_core::Error)` with `From` impls; `kind()` forwards to the inner error. `source()` returns the wrapped error.
4. **No panics in library code for any input that can reach a public API.** Every library crate root contains:
   `#![deny(clippy::unwrap_used, clippy::expect_used, clippy::panic, clippy::todo, clippy::unimplemented, clippy::indexing_slicing)]`
   Tests may opt out with `#[cfg_attr(test, allow(...))]` on the test module only. Validate lengths and parameters once at the public entry point; inner loops then iterate with `zip`, `chunks_exact`, `iter_mut` instead of indexing. Where indexing is unavoidable, use `.get()` and return `Error::Internal` if it ever fails.
5. Integer arithmetic that may overflow is written explicitly as `wrapping_*`, `saturating_*` or `checked_*`. The test profile keeps `overflow-checks = true`.

### R6 — Determinism and global state

1. No global mutable state: no `static mut`, no `static` with interior mutability (`Cell`, `RefCell`, `Mutex`, atomics, `OnceCell`, `LazyLock`), no `lazy_static`. Lookup tables are `const`/`static` immutable data, generated by `build.rs` where needed. `cargo xtask check` greps the source of library crates for these patterns and fails.
2. Same backend + same input = bit-identical output, independent of how the input is split into blocks. Every stateful kernel and block gets a block-size-invariance test (testkit helper from M03).
3. No reliance on CPU floating-point modes (flush-to-zero, rounding modes). Feedback states are flushed explicitly: `sdrk_core::num::flush_denormal(x)` returns 0.0 when `|x| < 1e-30`.
4. No hash-map iteration order in any output; use `BTreeMap` or ordered `Vec`s in upper layers.
5. Fused multiply-add is used only where the numeric contract allows it; the reference and the fallback never use FMA.
6. Little-endian only: `sdrk-device` contains `#[cfg(target_endian = "big")] compile_error!("sdrk supports little-endian targets only");`.

### R7 — Numeric conventions (from the plan's Decisions table)

| Topic | Rule |
| --- | --- |
| Q15 format | `Q15(i16)`, value = raw / 32768, range −1 … 1 − 2⁻¹⁵ |
| Rounding | round half up: add ½ LSB, then arithmetic right shift (`(x + (1 << (s - 1))) >> s` on a signed integer) |
| Overflow | always saturate to `[-32768, 32767]`, never wrap |
| Multiply | `sat16((a as i32 * b as i32 + (1 << 14)) >> 15)`; therefore `-1 × -1 = 32767` |
| Accumulation | reference and fallback accumulate Q30 products in `i64`, round and saturate once at the end; accelerated variants may use narrower accumulators if their headroom is documented |
| f32 → Q15 | computed in **f64**: `v = (x as f64) * 32768.0`; NaN → 0; otherwise `floor(v + 0.5)` clamped to `[-32768, 32767]` (so +1.0 → 32767, ±∞ → ±limit). Doing this in f32 would round twice and differ from the Python model |
| Q15 → f32 | `raw as f32 / 32768.0` (exact) |
| Complex Q15 | `CQ15 { re: Q15, im: Q15 }`, `#[repr(C)]`, I before Q — byte-identical to interleaved little-endian `cs16` |
| Denormals | flush feedback state to 0.0 below 1e-30 (R6.3) |
| Kernel classes | *bit-exact* kernels: fallback output equals the reference output bit for bit (Q15 and f32). *tolerance* kernels: output must reach the minimum SNR stated in the kernel's numeric contract (`docs/kernels.md`) against the f64 reference |

### R8 — Test vectors and golden samples (full specification in M04)

1. Golden samples live in `tests/golden/vectors/<kernel>/<case>.json` plus binary arrays `<case>.<array>.bin`. They are produced **only** by `tests/golden/generate.py` (Python 3.12, NumPy and SciPy with versions pinned exactly in `tests/golden/requirements.txt`). Never edit them by hand; never generate them with code from this repository.
2. Every case is deterministic: fixed seed via `numpy.random.default_rng(seed)`, fixed sizes, parameters stored in the JSON. Regenerating must produce byte-identical files (`python tests/golden/generate.py --check`).
3. Expected values are computed in float64 (`cf64`/`f64`). For bit-exact Q15 cases the generator computes the expected result with the integer model in `tests/golden/sdrk_golden/q15.py`, which implements R7 in NumPy `int64`.
4. Rust tests load cases with `sdrk_testkit::golden::load("<kernel>", "<case>")` (feature `std`). Tolerances live in the case JSON, not in Rust code.
5. Signal metric used everywhere: `SNR_dB = 10·log10( Σ|ref|² / Σ|ref − out|² )` over samples `skip..len` (`skip` stored per case; `+∞` when the error is zero). Bit-exact comparisons use `==` on raw bits. Tolerance classes (M04): `bit_exact`, `tolerance` (minimum SNR), `max_abs_err` (largest absolute error, optionally only where the reference is above a level).
6. Each case (JSON + all its `.bin` arrays) stays at or below 512 KiB; all vectors together at or below 32 MiB. Prefer N ≤ 4096 samples; use longer inputs only when the kernel needs them (long filters, decimation).
7. Tests that use `sdrk-testkit` live in integration tests (`<crate>/tests/*.rs`) or in `crates/testing/sdrk-testkit/tests/`, never in `#[cfg(test)]` unit modules of a crate the testkit itself depends on (a dev-dependency cycle would compile two copies of that crate and produce confusing trait errors).

## Specification

General rules of M19, M29 to M31, M44, M44.1 and their rounds apply. No aliases or old names are kept (no backward compatibility before 1.0): `order` of the six blocks is a hard rename, and an old flow that names it gets `unknown_parameter`.

### 1. The naming rule

1. **One name, one meaning:** a parameter that means the same thing has the same name and the same values in every block.
2. **One public parameter, once, to every building block that has it:** a parameter of a composite appears exactly once in the composite, and the composite passes its value unchanged to **every** building block that has a parameter of that name and meaning, for example `constellation` of `qam_demod` to `equalize`, `costas`, `symbol_demap` and `qam_acquire`, `symbol_rate_hz` to `pulse_match` and `symbol_sync`, and `constellation` of `qam_frame_decode` to `qam_demod` and `frame_decode` (which derives its bits per symbol from it, rule 4). The building blocks that share it have the same range and default. A composite has no code of its own that maps or converts a parameter; the user never sets the same thing twice.
3. **Same name, other meaning:** where two building blocks of a composite have a parameter with the same name but a different meaning, the composite gives each its own flat name by its role: `sync_bw` for `loop_bw` of `symbol_sync` (the symbol clock loop) and `carrier_bw` for `loop_bw` of `costas` (the carrier loop) in `qam_demod`; `equalizer_taps` for `taps` of `equalize`. This is a rename in the `ParamMap` table, never a change of the value.
4. **Derived values belong to the building block that uses them:** taps, samples per symbol from a rate and similar values are computed by the building block from its own parameters.
5. **A building block is a public pipeline kind only where it is useful on its own** (in a flow, for experiments), **where at least two composites use it, or where a use is planned in the backlog.** Otherwise it is a crate-internal Rust struct: tested the same way, but without a description, schema entry, factory, count entry or public documentation. Applied: `symbol_map`, `symbol_demap`, `pulse_shape`, `pulse_match` and `qam_acquire` stay kinds; `iq_offset` stays a kind (one user today, OQPSK in `psk_mod`; planned: IEEE 802.15.4 O-QPSK and FBMC/OQAM, backlog; maintainer decision of 2026-11-17); `LockWatch` and `FrameWatch` are internal already.
6. The rules are written into `docs/blocks.md` (section "Composite blocks") and checked by a test over every composite that lists its `ParamMap`: every public parameter appears once and maps to one or more building blocks, all with the same range and default, and every parameter of a building block that the composite exposes is reached by exactly one public parameter.

### 2. `constellation` instead of `order`

| Block | Parameter after M44.1.1 | Values | Default (the default of `order` before) |
|---|---|---|---|
| `qam_mod`, `qam_demod`, `qam_frame_encode`, `qam_frame_decode` | `constellation` | `qam16`, `qam64` (M44.2 adds `qam256`, `qam1024`) | `qam16` |
| `psk_mod`, `psk_demod` | `constellation` | `bpsk`, `qpsk`, `8psk` | `bpsk` |

- A value outside the block's set is `InvalidParameter` of `constellation` (`invalid_value` in the pipeline), as today for `order`. The checks that combine the order with other parameters (`differential`, `variant` of `psk_mod` and `psk_demod`, D648) read the constellation instead, with the same results.
- `qam_frame_encode` and `qam_frame_decode` derive the bits per symbol of `frame_encode` and `frame_decode` from the constellation inside the building blocks, not in the composite (§1.4).
- `QamModConfig`, `QamDemodConfig`, `PskModConfig`, `PskDemodConfig` and the configurations of the frame composites get a field `constellation` of the type the building blocks use; the field `order` goes.

### 3. Pulse filter building blocks

#### 3.1 `pulse_shape`

- `PulseShapeBlock` (`C32` symbols to `C32` samples): interpolates by `samples_per_symbol` with the taps `rrc(rolloff, sps, span) sqrt(sps)` rounded once to `f32` (`design::rrc`), through the kernel `fir_interpolate`, as `qam_mod` and `psk_mod` do today.
- Parameters: `samples_per_symbol` (2 to 64, required), `rolloff` (0.05 to 1, default 0.35), `span` (4 to 32 symbols, default 10), all build parameters, with the ranges of `psk_mod` and `qam_mod` today.
- Timing: constant ratio `sps`, the delay of today's modulators. Storage: the taps and the filter history.

#### 3.2 `pulse_match`

- `PulseMatchBlock` (`C32` to `C32` at the input rate): the matched filter `rrc(rolloff, n, span) / sqrt(n)` as `f32` through the kernel `fir`, with `n` from the rate rule of `psk_demod` and `qam_demod` (`fs / symbol_rate_hz` within 1 % of an integer from 2 to 1024; otherwise `InvalidParameter` of `symbol_rate_hz` with the hint to resample, `rate_unsupported` in the pipeline).
- Parameters: `symbol_rate_hz` (required), `rolloff` (default 0.35), `span` (default 10), all build parameters.
- Timing: ratio 1, the delay of the filter. Storage: the taps and the filter history.

#### 3.3 Composites

- `qam_mod` = `symbol_map` → `pulse_shape`; `psk_mod` = `symbol_map` → `pulse_shape` (→ `iq_offset` for the `offset` variant).
- `iq_offset` stays a pipeline kind (rule 5). It takes `samples_per_symbol` instead of `samples` and delays by half a symbol, `samples_per_symbol / 2` samples (the definition of OQPSK; an even `samples_per_symbol`, as `psk_mod` requires for `offset` today), so that `psk_mod` forwards `samples_per_symbol` unchanged (§1.4). `part` stays.
- `qam_demod` = `pulse_match` → `symbol_sync` → `qam_acquire` → `equalize` → `costas` → `symbol_demap` with the controller of M44.1.
- `InterpolateBlock::with_taps` (M44.1) is removed if nothing uses it any more (no dead code).
- The outputs are **bit-identical** to the blocks of M44.1 (its baselines, every case and cut plan), and the 512 / 2048 bytes of D1573 hold.

### 4. Forwarding through `ParamMap`

- **`ParamMap` fans out:** one flat name may map to several paths (today the first entry of a name wins, M31). `set` writes the value to every path, in the order of the table; if one building block rejects it, the composite returns that error and changes none of them (the building blocks are checked first, then written). `get` reads the first path; a test checks that all paths hold the same value.
- **Build parameters** (such as `constellation`) are handed to every building block that has them when the composite is built, from the one field of the composite's configuration.

- `qam_mod`, `psk_mod`, `qam_demod`, `qam_frame_encode` and `qam_frame_decode` answer `param` and `set_param` through `ParamMap` only; their own code that answers from a stored configuration (D1553) goes.
- The descriptions (`description()`, schema) of the composites list the same parameters as before with `order` replaced by `constellation`; ranges and defaults come from the building blocks.

### 5. Survey of the other composites

- Every other composite block (`ddc`, `duc`, `fm_demod`, `am_demod`, `ssb_demod`, `fm_stereo_demod`, `fsk_mod`, `fsk_demod`, `ook_demod`, `rds_demod`, and the others that `construction.rs` lists) is checked against §1. The result is a table in `docs/open-items.md` (one item): which composite converts which parameter. Nothing is changed in them in M44.1.1.

## Tests

Seeds 860 … 869.

1. **Bit identity:** every case of the M44.1 baselines (`qam_mod`, `psk_mod`, `qam_demod`, the BER, restart, recovery and flow tests) and their cut plans, with the flows renamed to `constellation` (seed 860).
2. **`pulse_shape` and `pulse_match`:** the taps equal `design::rrc` bit for bit; the outputs equal those of today's modulators and of the matched filter of `qam_demod`; the rate rule and its errors; chunk invariance with 20 plans (seed 861).

4. **`constellation`:** every valid and invalid value of the six blocks, the combinations with `differential` and `variant`, and `unknown_parameter` for `order` in a flow.
5. **Flows:** every flow of `examples/` that used `order` loads, validates and gives the same output as before (JSON and YAML).
