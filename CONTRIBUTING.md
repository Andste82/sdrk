# Contributing to SDRk

The full ground rules are repeated in every file under [docs/milestones](docs/milestones/README.md); this is the short form.

## Ground rules

- **R1 Work order:** milestones in numeric order, one branch and one pull request per milestone. Every milestone leaves `cargo fmt --all -- --check`, `cargo clippy --workspace --all-targets --all-features -- -D warnings`, `cargo test --workspace --all-features`, `cargo xtask check` and `cargo xtask bare-metal` green on Linux x86_64, Linux arm64 and Windows x86_64. Tools are Rust, no shell scripts. Judgement calls go into `docs/decisions-log.md`. Write **SDRk** only in prose, comments and docs; code uses lowercase `sdrk`.
- **R2 Layers:** the folder of a crate is its layer; a crate depends only on lower layers (`cargo xtask check layers`). Backends never depend on each other; only the facade knows them.
- **R3 `no_std`, no heap:** every crate up to and including `blocks` is `no_std` and allocation-free, memory comes from the caller, math from `libm`, at most 4 KiB stack per function.
- **R4 Clean interfaces:** small documented public API, `#[non_exhaustive]` for growing enums, validating constructors, one trait per kernel, no allocation, clock, randomness or printing in kernels, rustdoc with examples, all public types `Send`.
- **R5 Errors:** one scheme (`ErrorKind` / `SdrkError`), no panics in library code.
- **R6 Determinism:** no global mutable state, same backend and input give bit-identical output independent of block size, denormals flushed below 1e-30, little-endian only.
- **R7 Numerics:** Q15 conventions and the numeric contract of the plan.
- **R8 Test vectors:** golden vectors with fixed seeds, generated by the Python recipe of the milestone.
- **R9 Definition of done:** all commands pass, new public items documented, changelog and decisions log updated.

## Performance and accuracy

Every kernel change follows the measurement policy (decisions D32 to D34):

- **Compare like with like.** A SIMD branch is measured against an established library at the same level with the same algorithm and work, the fallback against established scalar code. Our own fallback is never the gate of a SIMD branch. See [docs/performance.md](docs/performance.md#measurement-policy).
- **Optimize for speed, not for fewer instructions.** The speed target is the simulated cycles per sample (and the efficiency) of every level with a core model: `sse2`, `sse4.2`, `avx2`, `avx512`, `neon` and the scalar fallback of each (D68; `cargo measure` reports them). Only the ratio ours / reference on the same model and from the same emulator counts. Instructions per sample are the gate for gross outliers there, and the gate and target on in-order cores and `simd128`; gates on cycles are not set yet. A SIMD branch without a fair reference is `info` with the reason in its `waiver` text. Working rule (D37, D68): shared code (the fallback, generic SIMD code) is optimized by the simulated cycles of every level; code of one level by the cycles of that level; `simd128` and in-order cores by instructions. See [docs/performance.md](docs/performance.md#working-rule-for-optimizing-d37-d68).
- **The golden is the accuracy target.** The f64 golden is the optimum; an established library is only a yardstick where the optimum cannot be reached. See [docs/kernels.md](docs/kernels.md#accuracy-policy).

## Versioning

`sdrk-device` aims at 1.0 early; all other crates stay 0.x until phase 9. While a crate is below 1.0, a breaking change bumps the minor version.

## Changelog

[Keep a Changelog](https://keepachangelog.com/en/1.1.0/) format in `CHANGELOG.md`; every user-visible change gets an entry under "Unreleased".

## Publishing order

`sdrk-device`, `sdrk-core`, the backends, `sdrk`, `sdrk-blocks`, `sdrk-io`, `sdrk-pipeline`, `sdrk-testkit`.
