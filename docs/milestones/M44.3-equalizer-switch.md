# M44.3 — Equalizer: the switch to decision mode on a measured criterion, and the restart of a false state

> Plan: [PLAN.md › Phase 10](../PLAN.md#phase-10--digital-modes) · Depends on: [M44.2](M44.2-qam-any-order.md) · Next: [BACKLOG](BACKLOG.md)

> **Status: done** (2026-11-21; §1 deferred to M44.4: the measured switch was built, measured and taken back out by the maintainer's decision on I44.3-4, D2424; §2 implemented and off, the decision when it restarts moved to M44.4, D2421; §3 done, test 7 passes; the cycles equal M44.2, D2425), the optimization round the maintainer decided on I44.2-3 (option (c)), I44.2-5 and I44.2-8 (D1517, D1528, D1541). Values marked *(to be confirmed)* are fixed by measurement through the decisions log.

## Goal

The blind equalizer of `qam_demod` (and the block `equalize`) switches from CMA to the decision mode when a measured criterion of the constellation says the CMA output is good enough, instead of after a fixed count of symbols; and an equalizer that sits in a false state without lock is started again. The acceptance test is test 7 of M44.2: the 256-QAM flow loop delivers at least 990 of 1000 packets.

## Why

- **The count is a worst case** (D1511, D1517): 16-QAM and 64-QAM switch after 1000 CMA symbols, 256-QAM after 8000, 1024-QAM after 16000. A good channel waits longer than it needs, and a hard one can switch too early into a false state.
- **No rule restarts a false state without lock** (I44.2-5, D1528): the recovery of M44.1 restarts by frequency, by the weight watch (only with lock) and after a gap. An equalizer whose blind start did not converge, while the loops sit on the right frequency, is never started again (2 of 9 receivers of 256-QAM through `Multipath::mild` with the blind start of D1511; 1024-QAM through `mild` no lock in 70000 symbols).
- **Test 7 of M44.2** delivers 930 of 1000 packets at Eb/N0 26 dB (961 at 28, 987 at 50 dB) because the 256-QAM decision mode settles slowly; every packet is lost until about symbol 40000 even without noise (D1534, D1541). Its code is on the branch `opt-round-qam256-test7`.

M44.3 starts after M44.2 (merged). It can run in parallel with M50 to M56; it does not touch their kernels.

### R3 — `no_std` and no heap (applies to every crate marked "yes" above)

1. The crate root starts with `#![no_std]`. The crate never writes `extern crate alloc;` and never uses `Vec`, `Box`, `String`, `Rc`, `Arc`, `BTreeMap` or anything else that allocates. `cargo xtask bare-metal` builds these crates for `thumbv7em-none-eabihf`, which has no global allocator, so any accidental allocation fails the build.
2. Memory is provided by the caller. State types are generic over their storage: a field that holds samples has a type parameter `S: AsRef<[T]> + AsMut<[T]>` (read-only data: `S: AsRef<[T]>`). On a microcontroller the caller passes `[T; N]` or `&mut [T]`; in upper layers the caller may pass `Vec<T>`. Constructors validate lengths and return `Err`, never panic.
3. Fixed-capacity containers come from `heapless` when needed.
4. No function may keep more than 4 KiB on its stack (WASM and MCU stacks are small). Large buffers belong in caller-provided storage. `clippy.toml` sets `stack-size-threshold = 4096` and the workspace enables `clippy::large_stack_frames` and `clippy::large_stack_arrays` as errors.
5. Math functions come from `libm` (e.g. `libm::sinf`, `libm::atan2f`, `libm::log10f`), never from `f32::sin()` & co. This keeps code `no_std` **and** makes results identical on every platform because `libm` is pure Rust.
6. Upper layers (`pipeline`, `io`, `bindings`, `examples`, `xtask`, testkit feature `std`) may use `std` and allocate. The only `std` use allowed below the heap boundary besides the testkit's `std` feature is runtime CPU-feature detection in backend crates behind their `std` feature (M13); it never allocates. The pipeline allocates only while *building*; after `build()` returns, processing must not allocate (tested with a counting global allocator in M10).

### R4 — Clean interfaces

1. Each crate exposes a small, documented public API through `lib.rs` re-exports; everything else is `pub(crate)`. Module layout inside a crate is an implementation detail.
2. Public enums that may grow are `#[non_exhaustive]`. Public structs with invariants have private fields, a validating constructor (`new(...) -> Result<Self>`) and getters.
3. Kernels follow the **one trait per kernel** pattern defined in M02: the trait is generic over the sample type, `Fallback` (in `sdrk-core`) implements it for every supported sample type, `Reference` (feature `reference`) implements it as the f64/integer specification, backends implement only the variants they accelerate, and the facade type `sdrk::Sdrk` implements all of them by delegating to the chosen implementation.
4. Kernel calls never allocate, never block, never read a clock, never use randomness, and never print.
5. Every public item has a rustdoc comment; every public function with non-trivial behaviour has a doc example that compiles (`#![deny(missing_docs)]` in every library crate; `cargo test --doc` runs the examples).
6. All public types are `Send`; state types and blocks are also `Sync` unless they need interior mutability (they should not). Add compile-time assertions in each crate's tests: `fn _assert_send<T: Send>() {}` called for every public type.

### R5 — One error-handling scheme for the whole workspace

1. The lowest crate `sdrk-device` defines the shared classification:
   ```rust
   #[derive(Debug, Clone, Copy, PartialEq, Eq, Hash)]
   #[non_exhaustive]
   pub enum ErrorKind {
       InvalidArgument, LengthMismatch, BufferTooSmall, OutOfRange, Unsupported,
       CapacityExceeded, InvalidState, ResourceLimit, Parse, Validation,
       Io, Device, Timeout, Disconnected, Internal,
   }
   pub trait SdrkError: core::error::Error {
       fn kind(&self) -> ErrorKind;
   }
   ```
2. Every library crate defines **its own** `pub enum Error` (`#[non_exhaustive]`, `Debug`, `Clone`, `PartialEq`) and `pub type Result<T, E = Error> = core::result::Result<T, E>;`. The enum implements `core::fmt::Display` (lowercase message, no trailing period), `core::error::Error` and `SdrkError`. Heap-free crates keep their error variants allocation-free (`&'static str` and integers only). Upper crates may carry `String` paths (e.g. `nodes.ddc.params.frequency_hz`).
3. Wrapping: an upper crate's error has a variant like `Core(sdrk_core::Error)` with `From` impls; `kind()` forwards to the inner error. `source()` returns the wrapped error.
4. **No panics in library code for any input that can reach a public API.** Every library crate root contains:
   `#![deny(clippy::unwrap_used, clippy::expect_used, clippy::panic, clippy::todo, clippy::unimplemented, clippy::indexing_slicing)]`
   Tests may opt out with `#[cfg_attr(test, allow(...))]` on the test module only. Validate lengths and parameters once at the public entry point; inner loops then iterate with `zip`, `chunks_exact`, `iter_mut` instead of indexing. Where indexing is unavoidable, use `.get()` and return `Error::Internal` if it ever fails.
5. Integer arithmetic that may overflow is written explicitly as `wrapping_*`, `saturating_*` or `checked_*`. The test profile keeps `overflow-checks = true`.

### R6 — Determinism and global state

1. No global mutable state: no `static mut`, no `static` with interior mutability (`Cell`, `RefCell`, `Mutex`, atomics, `OnceCell`, `LazyLock`), no `lazy_static`. Lookup tables are `const`/`static` immutable data, generated by `build.rs` where needed. `cargo xtask check` greps the source of library crates for these patterns and fails.
2. Same backend + same input = bit-identical output, independent of how the input is split into blocks. Every stateful kernel and block gets a block-size-invariance test (testkit helper from M03).
3. No reliance on CPU floating-point modes (flush-to-zero, rounding modes). Feedback states are flushed explicitly: `sdrk_core::num::flush_denormal(x)` returns 0.0 when `|x| < 1e-30`.
4. No hash-map iteration order in any output; use `BTreeMap` or ordered `Vec`s in upper layers.
5. Fused multiply-add is used only where the numeric contract allows it; the reference and the fallback never use FMA.
6. Little-endian only: `sdrk-device` contains `#[cfg(target_endian = "big")] compile_error!("sdrk supports little-endian targets only");`.

### R7 — Numeric conventions (from the plan's Decisions table)

| Topic | Rule |
| --- | --- |
| Q15 format | `Q15(i16)`, value = raw / 32768, range −1 … 1 − 2⁻¹⁵ |
| Rounding | round half up: add ½ LSB, then arithmetic right shift (`(x + (1 << (s - 1))) >> s` on a signed integer) |
| Overflow | always saturate to `[-32768, 32767]`, never wrap |
| Multiply | `sat16((a as i32 * b as i32 + (1 << 14)) >> 15)`; therefore `-1 × -1 = 32767` |
| Accumulation | reference and fallback accumulate Q30 products in `i64`, round and saturate once at the end; accelerated variants may use narrower accumulators if their headroom is documented |
| f32 → Q15 | computed in **f64**: `v = (x as f64) * 32768.0`; NaN → 0; otherwise `floor(v + 0.5)` clamped to `[-32768, 32767]` (so +1.0 → 32767, ±∞ → ±limit). Doing this in f32 would round twice and differ from the Python model |
| Q15 → f32 | `raw as f32 / 32768.0` (exact) |
| Complex Q15 | `CQ15 { re: Q15, im: Q15 }`, `#[repr(C)]`, I before Q — byte-identical to interleaved little-endian `cs16` |
| Denormals | flush feedback state to 0.0 below 1e-30 (R6.3) |
| Kernel classes | *bit-exact* kernels: fallback output equals the reference output bit for bit (Q15 and f32). *tolerance* kernels: output must reach the minimum SNR stated in the kernel's numeric contract (`docs/kernels.md`) against the f64 reference |

### R8 — Test vectors and golden samples (full specification in M04)

1. Golden samples live in `tests/golden/vectors/<kernel>/<case>.json` plus binary arrays `<case>.<array>.bin`. They are produced **only** by `tests/golden/generate.py` (Python 3.12, NumPy and SciPy with versions pinned exactly in `tests/golden/requirements.txt`). Never edit them by hand; never generate them with code from this repository.
2. Every case is deterministic: fixed seed via `numpy.random.default_rng(seed)`, fixed sizes, parameters stored in the JSON. Regenerating must produce byte-identical files (`python tests/golden/generate.py --check`).
3. Expected values are computed in float64 (`cf64`/`f64`). For bit-exact Q15 cases the generator computes the expected result with the integer model in `tests/golden/sdrk_golden/q15.py`, which implements R7 in NumPy `int64`.
4. Rust tests load cases with `sdrk_testkit::golden::load("<kernel>", "<case>")` (feature `std`). Tolerances live in the case JSON, not in Rust code.
5. Signal metric used everywhere: `SNR_dB = 10·log10( Σ|ref|² / Σ|ref − out|² )` over samples `skip..len` (`skip` stored per case; `+∞` when the error is zero). Bit-exact comparisons use `==` on raw bits. Tolerance classes (M04): `bit_exact`, `tolerance` (minimum SNR), `max_abs_err` (largest absolute error, optionally only where the reference is above a level).
6. Each case (JSON + all its `.bin` arrays) stays at or below 512 KiB; all vectors together at or below 32 MiB. Prefer N ≤ 4096 samples; use longer inputs only when the kernel needs them (long filters, decimation).
7. Tests that use `sdrk-testkit` live in integration tests (`<crate>/tests/*.rs`) or in `crates/testing/sdrk-testkit/tests/`, never in `#[cfg(test)]` unit modules of a crate the testkit itself depends on (a dev-dependency cycle would compile two copies of that crate and produce confusing trait errors).

## Specification

General rules of M44, M44.1, M44.1.1 and M44.2 apply, in particular the naming rules of composite parameters (D1823 to D1827): a parameter appears once, derived values belong to the building block, a composite may keep its own defaults.

### 1. The switch criterion

- `equalize` switches from CMA to the decision mode when a smoothed quality measure of its output falls below a threshold of the constellation for a hold time. The measure is chosen by measurement from:
  - the CMA dispersion `E[(|y|^2 - R2)^2]`, normalised by the constellation;
  - the decision error `E[|y - d(y)|^2]` relative to the half level spacing.
- The switch keeps:
  - a minimum count (no switch before it);
  - a maximum count (the count of D1517 / D1526 as a cap), so that a hard channel still switches.

  Both counts and the threshold are derived per constellation in the building block (rule 4) and logged.
- Measured against the counts of D1517 on the signals of D1511 (the kernel with the settings of `qam_demod`, a three-tap symbol-spaced channel turned by 0.3 rad, 8 seeds of 80000 symbols at the Eb/N0 of the BER tests) and on `Multipath::mild`, for every constellation:
  - the acquisition time (symbols to a correct lock);
  - the rate of false switches;
  - the MER after the switch.

  The criterion replaces the count only where it is at least as good on every one of these. Where it is not better for 16-QAM and 64-QAM, their outputs stay bit-identical (the baselines of M44.1 to M44.2).
- Parameters: the switch becomes the build parameter `blind_switch` of `equalize` (`count` or `measured`, the default chosen per constellation by the measurement, logged); `qam_demod` and `psk_demod` forward it unchanged (rule 2).

### 2. The restart of a false state

- `LockWatch` gets the transition that starts the equalizer again when, in `Verify`:
  - `n` checks in a row end without lock;
  - the estimate is clear and within the verify tolerance (the loops sit on the right frequency);
  - the criterion of §1 reports that the equalizer did not converge.

  The action is `RestartEqualizer` with the current estimate. `n` is *(to be confirmed, about 2)*.
- The restart must not fire on a weak signal that the loops hold (the cases of `a_weak_signal_the_loops_hold_is_not_restarted`, the 120 receivers of D1702 with their alignment changes).
- Measured on the signals of I44.2-5 (256-QAM and 1024-QAM through `mild` with the blind start of D1511, and the 2-of-9 cases): every receiver reaches a correct lock.

### 3. Test 7 and the settling of the dense orders

- Test 7 of M44.2, taken from the branch `opt-round-qam256-test7`: `qam256_transmitter` → channel (Eb/N0 26 dB, mild multipath, offset 1 kHz) → `qam256_receiver`, seeds 834 to 836 and every rotation. It must deliver at least 990 of 1000 packets `CRC_OK`; the bound is not lowered.
- If §1 and §2 are not enough, the settling of the decision mode of 256-QAM and 1024-QAM is improved: for example `mu_dd` per constellation during the first symbols of the decision mode, derived in the building block. Each step is measured and logged. A change of a maintainer decision (D1618 `mu_dd` 0.005 for 16-QAM and 64-QAM, D1706) needs the maintainer.
