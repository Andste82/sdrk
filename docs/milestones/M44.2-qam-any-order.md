# M44.2 — QAM of any square order (4, 16, 64, 256, 1024)

> Plan: [PLAN.md › Phase 10](../PLAN.md#phase-10--digital-modes) · Depends on: [M44](M44-qam.md), [M44.1](M44.1-qam-building-blocks.md) · Next: [BACKLOG](BACKLOG.md)

> **Status: implemented** (2026-11-19) on the branch `m44-2-qam-any-order-r` (the linear form of `m44-2-qam-any-order`, D1546), reviewed; I44.2-7 to I44.2-11 decided by the maintainer (D1540 to D1544), test 7 moved to the optimization round after M44.2 as its acceptance test (D1541); the GNU Radio references at 1024-QAM added (D1545), I44.2-12 accepted (D1547). Written as a draft on 2026-11-13 from a design discussion with the maintainer; the values marked *(to be confirmed)* are fixed by the implementation through the decisions log (D1500 to D1546).

> **4-QAM is QPSK (2026-11-17):** the 4-QAM grid of §1 with its Gray mapping is the QPSK of `psk_mod` point for point (`((2 b0 - 1) / sqrt 2, (2 b1 - 1) / sqrt 2)`). There is no constellation `qam4`: the QAM blocks accept `qpsk` as their smallest constellation, and the generic instance for one bit per axis serves `qpsk`. The implementation checks first that the soft bits of `symbol_demap` `qpsk` and of the generic instance are bit-identical; if their scales differ, one scale is chosen and logged (maintainer decision). Read `qpsk` wherever this file writes `qam4` or 4-QAM for a parameter value.

## Goal

`qam_mod` and `qam_demod` take any square order `M = 4^k` from 4 to 1024 (4, 16, 64, 256, 1024) instead of 16 and 64 only. Every QAM part becomes general in the order: the constellation tables, the soft bits (kernel `qam_soft_bits`), the grid decision, the CMA radius, the decision-directed carrier loop and its lock metric in `costas`, the equalizer's decision, the frequency acquisition of `qam_demod`, and the rotation map of `frame_decode`. The fast paths of 16-QAM and 64-QAM stay as fast as they are.

## Why

QAM gives the highest data rate per bandwidth. 256-QAM and 1024-QAM are what links with a good SNR use (cable, microwave links, Wi-Fi). Every part of M44 is built per axis on a square Gray grid, so the order is a parameter of formulas that already exist, not a new design. With one general path, any further square order needs no new code.

## Order

M44.2 depends on M44, on M44.1.1 (the parameter `constellation` instead of `order`; where this file writes `order` 4, 16, 64, 256, 1024 for a block, read `constellation` `qpsk`, `qam16`, `qam64`, `qam256`, `qam1024`), including its QAM round and the rounds of its open items (I44-1 to I44-18, D1400 to D1426 and D1600 and later). It starts after M44.1 (QAM in building blocks), because it generalises the building blocks that M44.1 makes of `qam_mod` and `qam_demod` (`symbol_map` with `qam4`, `qam256` and `qam1024`, `symbol_demap`, `equalize`, `costas`, `qam_acquire`) and not one large block; the composite blocks of M44.1 pass `order` on to them. Where this file names `qam_mod` and `qam_demod`, read "the composite block and its building blocks of M44.1". (Numbered M44.1 until 2026-11-15; renumbered when the building blocks were put before it.) It can run in parallel with M45.1, M46 and M48 to M56. QAM in Q15 is not part of it; that is a separate decision (D529).

### R3 — `no_std` and no heap (applies to every crate marked "yes" above)

1. The crate root starts with `#![no_std]`. The crate never writes `extern crate alloc;` and never uses `Vec`, `Box`, `String`, `Rc`, `Arc`, `BTreeMap` or anything else that allocates. `cargo xtask bare-metal` builds these crates for `thumbv7em-none-eabihf`, which has no global allocator, so any accidental allocation fails the build.
2. Memory is provided by the caller. State types are generic over their storage: a field that holds samples has a type parameter `S: AsRef<[T]> + AsMut<[T]>` (read-only data: `S: AsRef<[T]>`). On a microcontroller the caller passes `[T; N]` or `&mut [T]`; in upper layers the caller may pass `Vec<T>`. Constructors validate lengths and return `Err`, never panic.
3. Fixed-capacity containers come from `heapless` when needed.
4. No function may keep more than 4 KiB on its stack (WASM and MCU stacks are small). Large buffers belong in caller-provided storage. `clippy.toml` sets `stack-size-threshold = 4096` and the workspace enables `clippy::large_stack_frames` and `clippy::large_stack_arrays` as errors.
5. Math functions come from `libm` (e.g. `libm::sinf`, `libm::atan2f`, `libm::log10f`), never from `f32::sin()` & co. This keeps code `no_std` **and** makes results identical on every platform because `libm` is pure Rust.
6. Upper layers (`pipeline`, `io`, `bindings`, `examples`, `xtask`, testkit feature `std`) may use `std` and allocate. The only `std` use allowed below the heap boundary besides the testkit's `std` feature is runtime CPU-feature detection in backend crates behind their `std` feature (M13); it never allocates. The pipeline allocates only while *building*; after `build()` returns, processing must not allocate (tested with a counting global allocator in M10).

### R4 — Clean interfaces

1. Each crate exposes a small, documented public API through `lib.rs` re-exports; everything else is `pub(crate)`. Module layout inside a crate is an implementation detail.
2. Public enums that may grow are `#[non_exhaustive]`. Public structs with invariants have private fields, a validating constructor (`new(...) -> Result<Self>`) and getters.
3. Kernels follow the **one trait per kernel** pattern defined in M02: the trait is generic over the sample type, `Fallback` (in `sdrk-core`) implements it for every supported sample type, `Reference` (feature `reference`) implements it as the f64/integer specification, backends implement only the variants they accelerate, and the facade type `sdrk::Sdrk` implements all of them by delegating to the chosen implementation.
4. Kernel calls never allocate, never block, never read a clock, never use randomness, and never print.
5. Every public item has a rustdoc comment; every public function with non-trivial behaviour has a doc example that compiles (`#![deny(missing_docs)]` in every library crate; `cargo test --doc` runs the examples).
6. All public types are `Send`; state types and blocks are also `Sync` unless they need interior mutability (they should not). Add compile-time assertions in each crate's tests: `fn _assert_send<T: Send>() {}` called for every public type.

### R5 — One error-handling scheme for the whole workspace

1. The lowest crate `sdrk-device` defines the shared classification:
   ```rust
   #[derive(Debug, Clone, Copy, PartialEq, Eq, Hash)]
   #[non_exhaustive]
   pub enum ErrorKind {
       InvalidArgument, LengthMismatch, BufferTooSmall, OutOfRange, Unsupported,
       CapacityExceeded, InvalidState, ResourceLimit, Parse, Validation,
       Io, Device, Timeout, Disconnected, Internal,
   }
   pub trait SdrkError: core::error::Error {
       fn kind(&self) -> ErrorKind;
   }
   ```
2. Every library crate defines **its own** `pub enum Error` (`#[non_exhaustive]`, `Debug`, `Clone`, `PartialEq`) and `pub type Result<T, E = Error> = core::result::Result<T, E>;`. The enum implements `core::fmt::Display` (lowercase message, no trailing period), `core::error::Error` and `SdrkError`. Heap-free crates keep their error variants allocation-free (`&'static str` and integers only). Upper crates may carry `String` paths (e.g. `nodes.ddc.params.frequency_hz`).
3. Wrapping: an upper crate's error has a variant like `Core(sdrk_core::Error)` with `From` impls; `kind()` forwards to the inner error. `source()` returns the wrapped error.
4. **No panics in library code for any input that can reach a public API.** Every library crate root contains:
   `#![deny(clippy::unwrap_used, clippy::expect_used, clippy::panic, clippy::todo, clippy::unimplemented, clippy::indexing_slicing)]`
   Tests may opt out with `#[cfg_attr(test, allow(...))]` on the test module only. Validate lengths and parameters once at the public entry point; inner loops then iterate with `zip`, `chunks_exact`, `iter_mut` instead of indexing. Where indexing is unavoidable, use `.get()` and return `Error::Internal` if it ever fails.
5. Integer arithmetic that may overflow is written explicitly as `wrapping_*`, `saturating_*` or `checked_*`. The test profile keeps `overflow-checks = true`.

### R6 — Determinism and global state

1. No global mutable state: no `static mut`, no `static` with interior mutability (`Cell`, `RefCell`, `Mutex`, atomics, `OnceCell`, `LazyLock`), no `lazy_static`. Lookup tables are `const`/`static` immutable data, generated by `build.rs` where needed. `cargo xtask check` greps the source of library crates for these patterns and fails.
2. Same backend + same input = bit-identical output, independent of how the input is split into blocks. Every stateful kernel and block gets a block-size-invariance test (testkit helper from M03).
3. No reliance on CPU floating-point modes (flush-to-zero, rounding modes). Feedback states are flushed explicitly: `sdrk_core::num::flush_denormal(x)` returns 0.0 when `|x| < 1e-30`.
4. No hash-map iteration order in any output; use `BTreeMap` or ordered `Vec`s in upper layers.
5. Fused multiply-add is used only where the numeric contract allows it; the reference and the fallback never use FMA.
6. Little-endian only: `sdrk-device` contains `#[cfg(target_endian = "big")] compile_error!("sdrk supports little-endian targets only");`.

### R7 — Numeric conventions (from the plan's Decisions table)

| Topic | Rule |
| --- | --- |
| Q15 format | `Q15(i16)`, value = raw / 32768, range −1 … 1 − 2⁻¹⁵ |
| Rounding | round half up: add ½ LSB, then arithmetic right shift (`(x + (1 << (s - 1))) >> s` on a signed integer) |
| Overflow | always saturate to `[-32768, 32767]`, never wrap |
| Multiply | `sat16((a as i32 * b as i32 + (1 << 14)) >> 15)`; therefore `-1 × -1 = 32767` |
| Accumulation | reference and fallback accumulate Q30 products in `i64`, round and saturate once at the end; accelerated variants may use narrower accumulators if their headroom is documented |
| f32 → Q15 | computed in **f64**: `v = (x as f64) * 32768.0`; NaN → 0; otherwise `floor(v + 0.5)` clamped to `[-32768, 32767]` (so +1.0 → 32767, ±∞ → ±limit). Doing this in f32 would round twice and differ from the Python model |
| Q15 → f32 | `raw as f32 / 32768.0` (exact) |
| Complex Q15 | `CQ15 { re: Q15, im: Q15 }`, `#[repr(C)]`, I before Q — byte-identical to interleaved little-endian `cs16` |
| Denormals | flush feedback state to 0.0 below 1e-30 (R6.3) |
| Kernel classes | *bit-exact* kernels: fallback output equals the reference output bit for bit (Q15 and f32). *tolerance* kernels: output must reach the minimum SNR stated in the kernel's numeric contract (`docs/kernels.md`) against the f64 reference |

### R8 — Test vectors and golden samples (full specification in M04)

1. Golden samples live in `tests/golden/vectors/<kernel>/<case>.json` plus binary arrays `<case>.<array>.bin`. They are produced **only** by `tests/golden/generate.py` (Python 3.12, NumPy and SciPy with versions pinned exactly in `tests/golden/requirements.txt`). Never edit them by hand; never generate them with code from this repository.
2. Every case is deterministic: fixed seed via `numpy.random.default_rng(seed)`, fixed sizes, parameters stored in the JSON. Regenerating must produce byte-identical files (`python tests/golden/generate.py --check`).
3. Expected values are computed in float64 (`cf64`/`f64`). For bit-exact Q15 cases the generator computes the expected result with the integer model in `tests/golden/sdrk_golden/q15.py`, which implements R7 in NumPy `int64`.
4. Rust tests load cases with `sdrk_testkit::golden::load("<kernel>", "<case>")` (feature `std`). Tolerances live in the case JSON, not in Rust code.
5. Signal metric used everywhere: `SNR_dB = 10·log10( Σ|ref|² / Σ|ref − out|² )` over samples `skip..len` (`skip` stored per case; `+∞` when the error is zero). Tolerance classes (M04): `bit_exact`, `tolerance` (minimum SNR), `max_abs_err` (largest absolute error, optionally only where the reference is above a level).
6. Each case (JSON + all its `.bin` arrays) stays at or below 512 KiB; all vectors together at or below 32 MiB. Prefer N ≤ 4096 samples; use longer inputs only when the kernel needs them (long filters, decimation).
7. Tests that use `sdrk-testkit` live in integration tests (`<crate>/tests/*.rs`) or in `crates/testing/sdrk-testkit/tests/`, never in `#[cfg(test)]` unit modules of a crate the testkit itself depends on (a dev-dependency cycle would compile two copies of that crate and produce confusing trait errors).

## Scope

**In:**
- Square QAM orders 4, 16, 64, 256 and 1024 in the constellation tables of `sdrk-core::kernels::constellation`, in `qam_soft_bits`, `symbol_demap`, `equalize` and `costas`, in the blocks and kinds `qam_mod` and `qam_demod`, and in the frequency acquisition of `qam_demod`.
- `frame_decode` `bits_per_symbol` up to 10.
- One generic implementation of the soft bits (`qam_soft_bits`) and of the grid decision over the bits of the in-phase axis `BI` and of the quadrature axis `BQ` as compile-time constants (square grids have `BI` = `BQ`), instantiated for every square order (1 to 5 bits per axis), with SIMD on every level: every order gets a specialised path, and the formula is written once (§2, §3).
- Golden cases, tests, counts and cycles, and the docs: `docs/kernels.md`, `docs/blocks.md`, `docs/pipeline.md`, `docs/performance.md`, `examples/README.md` and `CHANGELOG.md`.

**Out:**
- Cross orders (`qam32_cross`, `qam128_cross`, `qam512_cross`): the corners of the grid are missing, so mapping, soft bits and decision are not per axis; backlog, with DVB-C.
- Rectangular orders (`qam8_rect`, `qam32_rect`, ...): they need no new code once the generic implementation takes `BI` and `BQ`; enabling their values (tables of points, the decision and the soft bits per axis with different `BI` and `BQ`, tests) is a later step on demand.
- APSK (`apsk16`, `apsk32`; backlog, with DVB-S2) and orders above 1024.
- QAM in Q15 (D529; a separate maintainer decision).
- FEC.

## Specification

General rules of M19 and of M44 apply. Wherever M44 names "16-QAM and 64-QAM", read "every order of §1".

### 1. Orders and constellation

- **Orders:** `M = 4^k` for `k` from 1 to 5, that is 4, 16, 64, 256 and 1024.
- **Grid:** `b = k` bits per axis, `m = 2^b` levels per axis and `2b` bits per symbol.
- **Mapping:** the same as M44 §1.
  - The first `b` bits select the in-phase level and the last `b` bits the quadrature level.
  - Each level index `i` uses the Gray code `i XOR (i >> 1)`, most significant bit first.
  - The level value is `2i − (m − 1)`.
  - The scale is `1/sqrt(E)` with `E = 2 (M − 1) / 3`. For the five orders `E` is 2, 10, 42, 170 and 682.
- **4-QAM** is the QPSK grid on the diagonals with this Gray mapping. It is a QAM order of `qam_mod` and `qam_demod`, not a replacement for `psk_mod` and `psk_demod` QPSK.
- **Decision:** per axis, round `(y·sqrt(E) + (m − 1)) / 2` and clamp it to `0 … m − 1` (M44 §1).
- **CMA radius:** `R2 = E|s|^4 / E|s|^2`, computed exactly from the integer grid.
  - The values are 1, 33/25, 29/21, 1.3953 and 1.3988 for 4, 16, 64, 256 and 1024.
  - The values for 4, 16 and 64 stay bit-identical.
  - 256 and 1024 are fractions of the same form (test to 4 digits).
- **Rotation by 90°:** the map of M44 §1 holds for every order. The bit groups `(I bits, Q bits)` go to `(Q bits with the first bit inverted, I bits)`. The test checks this for every symbol of every order.
- **Constant tables:** the tables are `const` data (R6). Every constant is checked bit for bit against `libm` as in M44.
- **Memory:** a 1024-QAM table of points is 1024 `C32`, 8 KiB. If a per-axis computation is as fast, it is preferred over the table (implementation choice, logged).

### Names of the constellations

One value of `constellation` names one grid, without ambiguity, in every block (M44.1.1):

| Grid | Values | Note |
|---|---|---|
| square QAM | `qam16`, `qam64`, `qam256`, `qam1024` | no suffix; 4-QAM is `qpsk` |
| cross QAM | `qam32_cross`, `qam128_cross`, `qam512_cross` | backlog (DVB-C) |
| rectangular QAM | `qam8_rect`, `qam32_rect`, `qam128_rect`, ... | on demand, through the generic implementation over `BI` and `BQ` |
| APSK | `apsk16`, `apsk32` | backlog (DVB-S2) |
| PSK | `bpsk`, `qpsk`, `8psk` | M40, M40.1 |

A bare `qam32` or `qam128` is not a value: the suffix says which grid is meant.

### 2. Soft bits (`qam_soft_bits`, `symbol_demap`)

The max-log piecewise-linear form of M44 §2, general for `b` bits per axis, with `v = y·sqrt(E)` per axis:

```
t_0 = v
t_i = 2^(b − i) − |t_{i−1}|      for i = 1 … b − 1
s_i = scale · t_i                (a soft bit > 0 means 1)
```

- For `b = 2` (16-QAM) this is `v` and `2 − |v|`. For `b = 3` (64-QAM) it is `v`, `4 − |v|` and `2 − ||v| − 4|`. The 16-QAM and 64-QAM outputs stay **bit-identical** to M44.
- The signs agree with the mapping of §1 for every level of every order up to `b = 5`, which was checked when this spec was written. The unit test derives them from the mapping as M44 does.
- **Paths of `qam_soft_bits`:**
  - **One generic implementation over `BI` and `BQ`** (the bits of the in-phase and of the quadrature axis, two `const` generic parameters; square grids have `BI` = `BQ` from 1 to 5, and a rectangular grid later only needs other values): the recursion above with `B` fixed at compile time, so that the compiler unrolls it and writes the soft bits of a symbol in their final order, as the hand-written paths of 16 and 64 do today. It is instantiated for every order (4, 16, 64, 256, 1024) and vectorised across symbols on every SIMD level; the order selects the instance. The formula exists once.
  - **16 and 64:** the instances for `B` = 2 and 3 replace the hand-written paths of M44 when their output is bit-identical (the baselines of M44.1) and their cycles per sample are at most those of the hand-written paths on every level and model. Where an instance is slower, the hand-written path stays for that order and level, with the numbers in the decisions log.
  - Every instance is at least as fast as the fallback of the same order (D321).
  - **Code size:** five instances per SIMD level. If the flash of a bare-metal target needs it, the orders above 64 can be left out by a cargo feature (default on); measured and logged.
  - The `symbol_demap` constellations (the kind `symbol_demap` until M44.1) become `qam4`, `qam16`, `qam64`, `qam256` and `qam1024`; `symbol_map` gets the same names. The existing constellation names stay.

### 3. Carrier loop and equalizer

- **`costas` `constellation`** gets `qam4`, `qam256` and `qam1024`.
  - The decision-directed QAM loop of M44 §3 is unchanged: `e = arg(y conj d)`, exact `atan2f`.
  - It uses the grid decision of §1.
  - The decision-error lock metric of D1400 uses the level spacing `delta` of the order, the same formula as for 16 and 64.
  - The lock threshold is checked for each order to stay off on noise (uniform and Gaussian) and on at the BER SNRs of the tests (*to be confirmed* per order).
- **`equalize` `constellation`** gets `qam4`, `qam256` and `qam1024`, with the decision of §1 and `R2` of §1.
  - CMA converges more slowly on the denser grids.
  - The default `cma_symbols` (1000) is checked for 256 and 1024 and raised by the block for these orders if needed (measured, logged).
- **Speed:**
  - The grid decision of `costas` and `equalize` is generic over `B` like the soft bits, instantiated for every order.
  - Its form is chosen per order and level by cycles plus mispredictions (D1611): the branch-free select tree of the speed round (D1416 to D1418, I44-11, I44-12; `B` levels per axis), a level table, or the rounding formula of §1. For 1024-QAM (five levels of the tree per axis) a table or the formula may win; the measurement decides, not an assumption.
  - For 16 and 64 the generic instances replace the specialised forms of D1416 to D1418 and I44-11 under the same conditions as the soft bits (bit-identical, not slower on any level and model); otherwise the specialised form stays for that order and level, logged.

### 4. Blocks and kinds `qam_mod`, `qam_demod`

- **`order`** becomes a choice of 4, 16, 64, 256 and 1024 (default 16). Any other value is `InvalidParameter`, and `invalid_value` in the pipeline.
- **Ratios and costs** follow `bits = log2(order)`. The kind costs of `qam_mod` and `qam_demod` (D1212) are checked per order.
- **`qam_demod`:**
  - The frequency acquisition of D1403 to D1405, D1421 the hysteresis of I44-9 (D1605 to D1608) and the restart check by frequency of I44-13 (D1618 to D1627) work for every order. The fourth power of every square grid has a line, `E[s^4]` = −1, −0.68, −0.62, −0.60 and −0.60 for the five orders, computed when this spec was written.
  - The self-noise grows with the order. The window of 512 symbols is checked per order and lengthened for 256 and 1024 if the detection rate or accuracy needs it (measured, logged).
  - The equalizer and carrier-loop defaults (`equalizer_taps`, `carrier_bw`, `sync_bw`) are checked per order.
- **`frame_decode` `bits_per_symbol`:** 1 to 10, even for `four`. The rotation map of §1 applies to groups of up to 10 bits.

### 5. Example flow

`qam256_transmitter` and `qam256_receiver` (JSON and YAML) are built like `qam16_transmitter` and `qam16_receiver`, with `order` 256, the rate and parameters chosen by measurement, `idle` `pn9`, and `rotations` `four` with `bits_per_symbol` 8. `examples/README.md` names them.
