# M44.1 — QAM in building blocks

> Plan: [PLAN.md › Phase 10](../PLAN.md#phase-10--digital-modes) · Depends on: [M44](M44-qam.md) (with the fix of I44-17), [M45](M45-channelizer.md) · Next: [M44.2](M44.2-qam-any-order.md)

> **Status: implemented** (2026-11-16, branch `m44-1-qam-building-blocks`, see [Status](#status)); the open items I44.1-2 to I44.1-5 are decided (D1587 to D1590, D1823, D1826), I44.1-6 is closed (D3161). Written on 2026-11-15 from a design discussion with the maintainer. Values marked *(to be confirmed)* are first estimates and are fixed by the implementation through the decisions log.

## Goal

QAM is built from small building blocks that each do one thing, and `qam_mod` and `qam_demod` become composite blocks of them, so that the same parts serve a single-carrier QAM link and, later, OFDM without being written twice:

- **New building blocks:** `symbol_map` (soft bits to the points of any constellation of `symbol_demap`, BPSK to 64-QAM, without pulse shaping), `iq_offset` (the OQPSK delay), `qam_acquire` (the frequency acquisition by the fourth power) and `LockWatch` (a supervisor that decides when a receiver starts again).
- **Control interface:** `equalize`, `costas` and `symbol_sync` get the few calls a controller needs (set a frequency or a phase, restart, read the weight energy).
- **Symmetric names** (the scheme of M24.1): `symbol_map` / `symbol_demap` (`slice` is renamed), `qam_mod` / `qam_demod`, `qam_frame_encode` / `qam_frame_decode`, one `iq_offset` for both sides.
- **Composite blocks:** `qam_mod` = `symbol_map` → interpolation with the RRC taps; `psk_mod` = `symbol_map` → interpolation (→ `iq_offset` for OQPSK); `qam_demod` = `fir` → `symbol_sync` → `qam_acquire` → `equalize` → `costas` → `symbol_demap`, held together by an explicit state machine instead of rules spread through one large block; and a new composite `qam_frame_decode` = `qam_demod` → `frame_decode` with a supervisor at frame level.
- **No error state lasts:** from every state the receiver returns to a correct lock in a bounded number of symbols when the signal allows it, which a new recovery test checks.

## Why

- **One computation exists once.** Today the constellation mapping lives in `qam_mod` and, a second time for BPSK to 8PSK, in `psk_mod`, the frequency acquisition and all of the control logic in `qam_demod`. OFDM needs the mapping and the soft bits per subcarrier, and a supervisor as much as a single-carrier receiver does; built into `qam_demod`, they would have to be written again.
- **The control logic becomes visible.** The rounds I44-3, I44-9, I44-13 and I44-17 each found an error case and added a rule (D1403 to D1405, D1421, D1605 to D1608, D1618 to D1627, D1700 to D1707). Together the rules are hard to see through, and I44-17 came from the interplay of two of them. A state machine with named states, conditions and time limits makes them reviewable and testable one by one.
- **Error states must not last** (maintainer decision on I44-17, D1707). Practical QAM receivers without pilots (cable, DVB-C, the DOCSIS downstream) solve this with a lock state machine that starts the chain again when the frame layer reports no sync for a while; SDRk has no such supervisor, and `qam_demod` cannot see whether frames come out.
- **Experiments.** A user who wants a simple receiver takes `qam_demod` or `qam_frame_decode`; one who experiments wires the building blocks in a flow (another synchronizer, no equalizer, own pilots).

## Order

M44.1 starts when the fix of I44-17 (PR #157) is merged. It comes before M44.2 (QAM of any square order), which then generalises the building blocks instead of one large block. The OFDM blocks of the backlog (`fft`/`ifft`, `to_lanes`/`from_lanes`, `subcarrier_map`/`subcarrier_demap`, `ofdm_mod`/`ofdm_demod`) and M55 (`pilot_equalize`) build on `symbol_map`, `symbol_demap` and `LockWatch`; no OFDM code is part of M44.1. It can run in parallel with M46 and M48 to M56.

### R3 — `no_std` and no heap (applies to every crate marked "yes" above)

1. The crate root starts with `#![no_std]`. The crate never writes `extern crate alloc;` and never uses `Vec`, `Box`, `String`, `Rc`, `Arc`, `BTreeMap` or anything else that allocates. `cargo xtask bare-metal` builds these crates for `thumbv7em-none-eabihf`, which has no global allocator, so any accidental allocation fails the build.
2. Memory is provided by the caller. State types are generic over their storage: a field that holds samples has a type parameter `S: AsRef<[T]> + AsMut<[T]>` (read-only data: `S: AsRef<[T]>`). On a microcontroller the caller passes `[T; N]` or `&mut [T]`; in upper layers the caller may pass `Vec<T>`. Constructors validate lengths and return `Err`, never panic.
3. Fixed-capacity containers come from `heapless` when needed.
4. No function may keep more than 4 KiB on its stack (WASM and MCU stacks are small). Large buffers belong in caller-provided storage. `clippy.toml` sets `stack-size-threshold = 4096` and the workspace enables `clippy::large_stack_frames` and `clippy::large_stack_arrays` as errors.
5. Math functions come from `libm` (e.g. `libm::sinf`, `libm::atan2f`, `libm::log10f`), never from `f32::sin()` & co. This keeps code `no_std` **and** makes results identical on every platform because `libm` is pure Rust.
6. Upper layers (`pipeline`, `io`, `bindings`, `examples`, `xtask`, testkit feature `std`) may use `std` and allocate. The only `std` use allowed below the heap boundary besides the testkit's `std` feature is runtime CPU-feature detection in backend crates behind their `std` feature (M13); it never allocates. The pipeline allocates only while *building*; after `build()` returns, processing must not allocate (tested with a counting global allocator in M10).

### R4 — Clean interfaces

1. Each crate exposes a small, documented public API through `lib.rs` re-exports; everything else is `pub(crate)`. Module layout inside a crate is an implementation detail.
2. Public enums that may grow are `#[non_exhaustive]`. Public structs with invariants have private fields, a validating constructor (`new(...) -> Result<Self>`) and getters.
3. Kernels follow the **one trait per kernel** pattern defined in M02: the trait is generic over the sample type, `Fallback` (in `sdrk-core`) implements it for every supported sample type, `Reference` (feature `reference`) implements it as the f64/integer specification, backends implement only the variants they accelerate, and the facade type `sdrk::Sdrk` implements all of them by delegating to the chosen implementation.
4. Kernel calls never allocate, never block, never read a clock, never use randomness, and never print.
5. Every public item has a rustdoc comment; every public function with non-trivial behaviour has a doc example that compiles (`#![deny(missing_docs)]` in every library crate; `cargo test --doc` runs the examples).
6. All public types are `Send`; state types and blocks are also `Sync` unless they need interior mutability (they should not). Add compile-time assertions in each crate's tests: `fn _assert_send<T: Send>() {}` called for every public type.

### R5 — One error-handling scheme for the whole workspace

1. The lowest crate `sdrk-device` defines the shared classification:
   ```rust
   #[derive(Debug, Clone, Copy, PartialEq, Eq, Hash)]
   #[non_exhaustive]
   pub enum ErrorKind {
       InvalidArgument, LengthMismatch, BufferTooSmall, OutOfRange, Unsupported,
       CapacityExceeded, InvalidState, ResourceLimit, Parse, Validation,
       Io, Device, Timeout, Disconnected, Internal,
   }
   pub trait SdrkError: core::error::Error {
       fn kind(&self) -> ErrorKind;
   }
   ```
2. Every library crate defines **its own** `pub enum Error` (`#[non_exhaustive]`, `Debug`, `Clone`, `PartialEq`) and `pub type Result<T, E = Error> = core::result::Result<T, E>;`. The enum implements `core::fmt::Display` (lowercase message, no trailing period), `core::error::Error` and `SdrkError`. Heap-free crates keep their error variants allocation-free (`&'static str` and integers only). Upper crates may carry `String` paths (e.g. `nodes.ddc.params.frequency_hz`).
3. Wrapping: an upper crate's error has a variant like `Core(sdrk_core::Error)` with `From` impls; `kind()` forwards to the inner error. `source()` returns the wrapped error.
4. **No panics in library code for any input that can reach a public API.** Every library crate root contains:
   `#![deny(clippy::unwrap_used, clippy::expect_used, clippy::panic, clippy::todo, clippy::unimplemented, clippy::indexing_slicing)]`
   Tests may opt out with `#[cfg_attr(test, allow(...))]` on the test module only. Validate lengths and parameters once at the public entry point; inner loops then iterate with `zip`, `chunks_exact`, `iter_mut` instead of indexing. Where indexing is unavoidable, use `.get()` and return `Error::Internal` if it ever fails.
5. Integer arithmetic that may overflow is written explicitly as `wrapping_*`, `saturating_*` or `checked_*`. The test profile keeps `overflow-checks = true`.

### R6 — Determinism and global state

1. No global mutable state: no `static mut`, no `static` with interior mutability (`Cell`, `RefCell`, `Mutex`, atomics, `OnceCell`, `LazyLock`), no `lazy_static`. Lookup tables are `const`/`static` immutable data, generated by `build.rs` where needed. `cargo xtask check` greps the source of library crates for these patterns and fails.
2. Same backend + same input = bit-identical output, independent of how the input is split into blocks. Every stateful kernel and block gets a block-size-invariance test (testkit helper from M03).
3. No reliance on CPU floating-point modes (flush-to-zero, rounding modes). Feedback states are flushed explicitly: `sdrk_core::num::flush_denormal(x)` returns 0.0 when `|x| < 1e-30`.
4. No hash-map iteration order in any output; use `BTreeMap` or ordered `Vec`s in upper layers.
5. Fused multiply-add is used only where the numeric contract allows it; the reference and the fallback never use FMA.
6. Little-endian only: `sdrk-device` contains `#[cfg(target_endian = "big")] compile_error!("sdrk supports little-endian targets only");`.

### R7 — Numeric conventions (from the plan's Decisions table)

| Topic | Rule |
| --- | --- |
| Q15 format | `Q15(i16)`, value = raw / 32768, range −1 … 1 − 2⁻¹⁵ |
| Rounding | round half up: add ½ LSB, then arithmetic right shift (`(x + (1 << (s - 1))) >> s` on a signed integer) |
| Overflow | always saturate to `[-32768, 32767]`, never wrap |
| Multiply | `sat16((a as i32 * b as i32 + (1 << 14)) >> 15)`; therefore `-1 × -1 = 32767` |
| Accumulation | reference and fallback accumulate Q30 products in `i64`, round and saturate once at the end; accelerated variants may use narrower accumulators if their headroom is documented |
| f32 → Q15 | computed in **f64**: `v = (x as f64) * 32768.0`; NaN → 0; otherwise `floor(v + 0.5)` clamped to `[-32768, 32767]` (so +1.0 → 32767, ±∞ → ±limit). Doing this in f32 would round twice and differ from the Python model |
| Q15 → f32 | `raw as f32 / 32768.0` (exact) |
| Complex Q15 | `CQ15 { re: Q15, im: Q15 }`, `#[repr(C)]`, I before Q — byte-identical to interleaved little-endian `cs16` |
| Denormals | flush feedback state to 0.0 below 1e-30 (R6.3) |
| Kernel classes | *bit-exact* kernels: fallback output equals the reference output bit for bit (Q15 and f32). *tolerance* kernels: output must reach the minimum SNR stated in the kernel's numeric contract (`docs/kernels.md`) against the f64 reference |

### R8 — Test vectors and golden samples (full specification in M04)

1. Golden samples live in `tests/golden/vectors/<kernel>/<case>.json` plus binary arrays `<case>.<array>.bin`. They are produced **only** by `tests/golden/generate.py` (Python 3.12, NumPy and SciPy with versions pinned exactly in `tests/golden/requirements.txt`). Never edit them by hand; never generate them with code from this repository.
2. Every case is deterministic: fixed seed via `numpy.random.default_rng(seed)`, fixed sizes, parameters stored in the JSON. Regenerating must produce byte-identical files (`python tests/golden/generate.py --check`).
3. Expected values are computed in float64 (`cf64`/`f64`). For bit-exact Q15 cases the generator computes the expected result with the integer model in `tests/golden/sdrk_golden/q15.py`, which implements R7 in NumPy `int64`.
4. Rust tests load cases with `sdrk_testkit::golden::load("<kernel>", "<case>")` (feature `std`). Tolerances live in the case JSON, not in Rust code.
5. Signal metric used everywhere: `SNR_dB = 10·log10( Σ|ref|² / Σ|ref − out|² )` over samples `skip..len` (`skip` stored per case; `+∞` when the error is zero). Bit-exact comparisons use `==` on raw bits. Tolerance classes (M04): `bit_exact`, `tolerance` (minimum SNR), `max_abs_err` (largest absolute error, optionally only where the reference is above a level).
6. Each case (JSON + all its `.bin` arrays) stays at or below 512 KiB; all vectors together at or below 32 MiB. Prefer N ≤ 4096 samples; use longer inputs only when the kernel needs them (long filters, decimation).
7. Tests that use `sdrk-testkit` live in integration tests (`<crate>/tests/*.rs`) or in `crates/testing/sdrk-testkit/tests/`, never in `#[cfg(test)]` unit modules of a crate the testkit itself depends on (a dev-dependency cycle would compile two copies of that crate and produce confusing trait errors).

## Specification

General rules of M19, M29 to M31 (composite blocks), M44 and its rounds apply. Every number of a building block (window lengths, bandwidths, tolerances, thresholds) keeps the value and the name it has in `qam_demod` today; this milestone moves code, it does not retune it, except where §6 says so.

### 1. Layers

- **Kernels** (unchanged): the constellation tables, `qam_soft_bits`, `fft`, `fir`, `fir_interpolate`, `symbol_sync`, `equalize`, `costas`.
- **Building blocks**: ordinary blocks and pipeline kinds, each around one task. A building block holds the state of its task and nothing of another task.
- **Composite blocks**: blocks of building blocks plus at most a controller. A composite has no signal computation of its own: every sample it writes comes from a building block. Its controller reads the building blocks and calls their control interface (§3) between the calls of their `process`.
- **The 512-byte rule** (blocks.md, `construction.rs`) holds for every building block and every composite. If a composite cannot hold its building blocks within 512 bytes, the implementation records the sizes and the maintainer decides (for example, the building blocks' configuration out of the struct into the storage); the rule is not loosened without that decision.

### 2. New building blocks

#### 2.1 `symbol_map`

- `SymbolMapBlock` (`f32` soft bits to `C32`): the mapping of bits to one symbol of a constellation, without pulse shaping, the transmit side of `symbol_demap`. It replaces the mappings inside `qam_mod` (M44 §1) and `psk_mod` (M40, M40.1), so the mapping exists once for every single-carrier modulator and, later, for the subcarriers of OFDM.
- Parameter `constellation`: `bpsk`, `qpsk`, `8psk`, `qam16` or `qam64` (the names of `symbol_demap`; `real` and `fsk4` of `symbol_demap` have no transmit mapping here). Bits per symbol: 1, 2, 3, 4 and 6. Soft bits `> 0` are a 1, NaN a 0, the first bit the most significant.
- The points are those of today's blocks, bit for bit:
  - `bpsk`, `qpsk`, `8psk`: the sixteen constant `f32` points at multiples of 22.5 degrees of `psk_mod` (D649) and its Gray tables (`PSK8_GRAY`, the convention of `symbol_demap`);
  - `qam16`, `qam64`: the table of `sdrk_core::kernels::constellation::Qam` (shared with `symbol_demap`, `equalize` and `costas`).
- Parameter `differential` (default `false`; `bpsk`, `qpsk` and `8psk` only): the phase is kept as a multiple of 22.5 degrees (modulo 16) and advanced by the phase of the mapped symbol, start phase 0 (D613).
- Parameter `variant` (default `plain`): `plain` or `pi4` (pi/4-DQPSK, `qpsk` with `differential` only, the phase steps of D648). Every other combination is `InvalidParameter` of the parameter that makes it invalid (`invalid_value` in the pipeline). The `offset` variant of `psk_mod` (OQPSK) acts after the pulse filter and is the building block `iq_offset` (§2.4), not a mapping.
- All parameters are build parameters. Timing: constant ratio `1 / bits`, delay 0, `min_input` `bits`. Storage: none (the differential phase is a counter in the struct). Pipeline cost: one table lookup per output sample *(the cost formula to be confirmed by the counts)*.

#### 2.2 `qam_acquire`

- `QamAcquireBlock` (`C32` symbols to `C32` symbols, one sample per symbol): the frequency acquisition of `qam_demod` (D1403 to D1405, D1421) as its own block: windows of `QAM_ACQUISITION_SYMBOLS` (512) symbols of `x^4 / p^2` from symbol `QAM_ACQUISITION_SKIP` (256) on, zero-padded to 1024 points through `fft`, the largest bin refined by a parabola, range ±0.125 cycles per symbol, an estimate when the peak is at least 12 times the energy of the window.
- Parameter `correct` (`false` or `true`, default `false`):
  - `false`: the output is the input, bit for bit; the block only estimates. This is the mode of the composite `qam_demod`, whose controller reads the estimate.
  - `true`: the output is the input turned back by the estimate (`x[n] · exp(−j 2π f n)`, the phase kept continuous across estimates), so that the block is useful in a flow of its own, for example in front of a `costas`.
- Interface: `estimate() -> Option<f64>` (cycles per symbol), `window_clear() -> Option<bool>` (whether the last completed window had a clear peak; `None` before the first window), `search()` (start a new search: drop the estimate and begin a window at the next symbol), `verify()` (take one window as the verify window of D1619 and report it without replacing the estimate).
- Storage: the 1024 `C32` of the FFT and its 512 twiddles, as in `qam_demod` today.

#### 2.3 `LockWatch`

A heap-free supervisor type (not a block and not a kind) that a composite feeds once per check and that answers what to do. It holds the states and time limits of §5 and is shared by `qam_demod`, `qam_frame_decode` and, later, `ofdm_demod`.

- **Inputs per check:** the lock of the carrier loop, the result of the last acquisition window (clear or not, the estimate), the weight energy of the equalizer (when there is one), and, in `qam_frame_decode`, the number of frames with `CRC_OK` since the last check.
- **Outputs:** one of `Keep`, `Verify`, `RestartEqualizer`, `RestartAll`.
- **Parameters** (fixed by the composite, not pipeline parameters): the thresholds and time limits of §5 and §6.
- Unit-testable on its own with scripted inputs.

#### 2.4 `iq_offset`

- `IqOffsetBlock` (`C32` to `C32`): delays one part of the signal by `samples` samples against the other, through a ring of `samples` `f32` in the storage, zeros at the start and after `reset`. It is the same operation on both sides of an OQPSK link: the transmitter delays the imaginary part (the step of `psk_mod` `variant` `offset`, D650), a receiver delays the real part by the same amount to align the two again.
- Parameters `samples` (1 to 512, required; `psk_mod` uses `sps / 2`) and `part` (`imag` or `real`, default `imag`), both build parameters. Timing: constant ratio 1, delay 0 (the other part is not delayed, as in `psk_mod`), `min_input` 1. `psk_demod` keeps its own offset path in M44.1 (§4).

### 3. Control interface of the building blocks

The building blocks get these methods (Rust API only; no pipeline parameters, no change of their output while nobody calls them):

| Block | Methods |
|---|---|
| `EqualizeBlock` | `set_frequency(f64)`, `set_phase(u32)`, `set_phase_bw(f64)`, `restart()` (start weights, history cleared, blind mode with its CMA count), `weight_energy() -> f32` (sum of `|w|²`), `mode()`, `mse()` (exist) |
| `CostasBlock` | `set_frequency(f64)`, `restart()`, `lock_level() -> f32`, `locked()`, `frequency()` (exist) |
| `SymbolSyncBlock` | `restart()` |

Each is what `qam_demod` does today on the states (`EqualizeState::set_frequency`, `set_phase`, `set_phase_bw` of D1622 and D1700, and so on); the methods forward to the states.

### 4. Composite modulators `qam_mod` and `psk_mod`

- `qam_mod` = `symbol_map` (`qam16` or `qam64` from `order`) → an interpolation stage with the taps `rrc(rolloff, sps, span) sqrt(sps)` as `f32` (the kernel `fir_interpolate`), as a `Chain`.
- The block `interpolate` designs its own Kaiser low-pass taps from `cutoff` and `transition`; the stage needs given taps. `InterpolateBlock` gets a constructor from given taps (Rust API, `InterpolateBlock::with_taps`), which both composites use.
- `psk_mod` = `symbol_map` (`bpsk`, `qpsk` or `8psk` from `order`, with `differential` and `variant` `plain` or `pi4`) → the same interpolation stage → for `variant` `offset` `iq_offset` with `samples` = `sps / 2`.
- Parameters, timing, ratio, delay and pipeline cost of both stay those of M44 §4, D1212 and M40, M40.1 (`psk_mod` keeps `order`, `differential` and `variant` as its public parameters and maps them through `ParamMap`).
- The outputs are **bit-identical** to the `qam_mod` and `psk_mod` of `main` before M44.1 for every test of M40, M40.1 and M44, every combination of `order`, `differential` and `variant`, and for 20 random cut plans.
- `psk_demod` is not changed in M44.1: its coherent, differential and offset paths are a round of their own, once M44.1 has shown the pattern.

### 5. Composite `qam_demod` (step 1: the same behaviour)

- `qam_demod` holds `fir`, `symbol_sync`, `qam_acquire` (`correct` false), `equalize` (for `equalizer_taps` above 0), `costas` and `symbol_demap`, and a controller.
- **The controller is a state machine** with these states; every rule of today's block maps to exactly one transition, named in the code and in `docs/blocks.md`:

  | State | What runs | Leaves when |
  |---|---|---|
  | `Search` | the acquisition searches; equalizer blind; loops at frequency 0 | a clear estimate → `PullIn` (the estimate to the equalizer's tracker at `QAM_TRACKER_PULL_BW`, or to `costas` without the equalizer) |
  | `PullIn` | equalizer blind, then the hand-over of D1700 at the switch to decisions | the first check after the estimate → `Track` (tracker to `QAM_TRACKER_HOLD_BW`) |
  | `Track` | everything; check every `QAM_ACQUISITION_CHECK` (4096) symbols | a check without lock → `Verify` |
  | `Verify` | one verify window (D1619) | a clear estimate more than `QAM_ACQUISITION_VERIFY_TOLERANCE` (2e-4) from the loops → `Search` with a restart of the equalizer; otherwise → `Track` |

- **Bit identity:** in step 1 the soft bits are **bit-identical** to the `qam_demod` of `main` with the fix of I44-17, on every signal of `qam_ber_m44`, `qam_restart_m44`, `qam_blocks` and the flow test, and for 20 random cut plans. The splits of the calls at the symbol where a window completes, a check falls or the hand-over happens (D1403, D1700) stay exactly where they are.
- `locked()`, `lock_level()`, `frequency()`, `acquired_frequency()`, `restarts()`, `equalizer()` and `sps_estimate()` keep their meaning; new `state()` returns the state of the controller.
- Parameters, timing and pipeline cost stay those of M44 §4 and its rounds.

### 6. Recovery (step 2: no error state lasts)

The maintainer's rule (D1707): an error state of the receiver must not last. Two conditions join the transitions of §5, both inside `LockWatch`:

1. **Weight watch.** In `Track`, a weight energy of the equalizer below `QAM_WATCH_WEIGHT_ENERGY` on `QAM_WATCH_CHECKS` checks in a row → `Search` with a restart of the equalizer. First values: 0.85 and 2 *(to be confirmed: the energy is 0.96 to 0.99 in a correct lock and 0.50 to 0.71 in the false states of D1700 and of the gap case; the threshold must hold on every multipath case of the tests, where the correct weights can carry less energy)*.
2. **Signal back after a gap.** A clear acquisition window after at least `QAM_WATCH_GAP_WINDOWS` windows in a row without one → `RestartEqualizer`, then `PullIn` with the new estimate. First value: 3 *(to be confirmed; a hysteresis, so that weak signals whose windows alternate between clear and not clear, D1619, are not started again)*.

Each new constant is measured, logged and named. Neither condition may restart a receiver that holds a weak signal (the cases of `a_weak_signal_the_loops_hold_is_not_restarted`).

### 7. Composites `qam_frame_encode` and `qam_frame_decode`

- `qam_frame_decode` = `qam_demod` → `frame_decode` (`rotations` `four`, `bits_per_symbol` of the order) with a frame-level watch: no frame with `CRC_OK` for `frame_timeout` symbols while frames are expected → `RestartAll` of the inner `qam_demod`.
- Parameters: those of `qam_demod` and of `frame_decode` (flat names through `ParamMap`), and `frame_timeout` (symbols, default *(to be confirmed, about 4 checks, 16384 symbols)*, 0 = off). "Frames expected" is the maintainer's choice of the implementation's options *(to be confirmed: always, or only after a first `CRC_OK` since the start or a restart)*.
- Input `C32`, output `Packets`, as the pair `qam_demod` → `frame_decode` has today.
- `qam_frame_encode` = `frame_encode` → `qam_mod`, the transmit side: packets to `C32` samples, with the parameters of both (flat names through `ParamMap`). Its output is bit-identical to the pair `frame_encode` → `qam_mod` it replaces.
- The flows `qam16_transmitter` and `qam16_receiver` (JSON and YAML) use `qam_frame_encode` and `qam_frame_decode`; `examples/README.md` names them.
- Both names follow rule 4 of the naming scheme (samples on one side, packets on the other are `_encode` / `_decode`).

### 8. Speed

- Cycles per sample (whole-loop, reference / counter model per level, the corrected `llvm-mca` of D942) of `qam_mod_block`, `psk_mod_block` (a new entry; its baseline is measured on `main` before the change), `qam_demod_block` and `qam_demod_search_block` are measured before and after on every level with a core model; instructions only where no cycles exist (simd128), marked.
- The goal is no regression on any level and model. A composite may add copies between building blocks; if one entry gets slower by more than 1 % on a level and model, the implementation first tries the forms of M31 (one buffer per chain, `Chain` with pairs), then reports the numbers, and the maintainer decides.
- Data-dependent branches of the controller are judged by D1611 (cycles plus mispredictions times the penalties of D1612 and D1628). The controller runs once per check or per piece, not per symbol, wherever the behaviour allows it.

### 9. Names

The kinds of M44.1 follow the naming scheme of M24.1 (`docs/blocks.md`, section "Names") and come in pairs where a link has two sides:

| Transmit side | Receive side | Note |
|---|---|---|
| `symbol_map` | `symbol_demap` | `slice` is renamed to `symbol_demap` (kind, `SymbolDemapBlock`, `SymbolDemapConfig`, `blocks/symbol_demap.rs`, the count entries `slice_*_block` to `symbol_demap_*_block`, every flow, test and doc); a hard rename without an alias (no aliases before 1.0). The kernels keep their names (`qam_soft_bits` and the per-constellation code of the block; rule 8). The pair matches `subcarrier_map` / `subcarrier_demap` of OFDM. |
| `qam_mod`, `psk_mod` | `qam_demod`, `psk_demod` | unchanged |
| `qam_frame_encode` | `qam_frame_decode` | new composites (§7) |
| `iq_offset` | `iq_offset` | one kind, parameter `part` (§2.4) |
| – | `qam_acquire`, `symbol_sync`, `equalize`, `costas` | receive-only tasks; a transmitter has no counterpart |

The new kinds are added to the table of reserved names in `docs/blocks.md` (done with this spec), and `cargo xtask check` (names) passes on them.
