# Golden vectors

Golden vectors validate the Rust kernels against an independent implementation: NumPy/SciPy for float
kernels and the Python Q15 integer model (`sdrk_golden/q15.py`) for bit-exact Q15 kernels. The files in
`vectors/` are committed to git and read by `sdrk_testkit::golden` (feature `std`). Never edit them by
hand and never generate them with code from this repository.

The golden of a tolerance case is the mathematical optimum: the result computed in `f64`, treated as
exact (except `squelch`, `stereo_pll` and `preemph_limit`, whose cases come from an exact float32 or integer model, see `docs/kernels.md`). It is the
first accuracy target of a kernel, not only a pass/fail check. The `snr_db_min` stored in a case is the contract
floor; the accuracy policy in [`docs/kernels.md`](../../docs/kernels.md#accuracy-policy) adds the
achievable optimum and a regression guard close to the measured SNR. A bit-exact Q15 case proves agreement
with our own integer model, not closeness to the optimum; the policy adds an SNR check against an `f64`
golden for those kernels.

**Report.** When the environment variable `SDRK_GOLDEN_REPORT` names a file, every comparison of
`sdrk_testkit::golden::assert_matches` appends one JSON line to it: the case, the sample type, the class,
the floor, the achieved SNR, the achievable optimum (the expected values rounded once to the sample type) and
whether it passed. `assert_matches_block_float` does the same for a block-floating-point `CQ15` output; its
optimum is the expected values rounded to a Q15 mantissa with the block exponent they need. `cargo measure <kernel>` uses it (`docs/performance.md`).

## Setup

```sh
python3.12 -m venv .venv && . .venv/bin/activate && pip install -r tests/golden/requirements.txt
```

On Windows activate with `.venv\Scripts\activate`. The versions in `requirements.txt` are pinned exactly;
byte-identical output is only guaranteed with those versions and Python 3.12, **on Linux x86-64**.

**Generate the vectors on Linux x86-64 only.** The generator runs on every host (R1.3, checked by CI),
but NumPy and SciPy evaluate `cos`, `exp`, the FFT and the filter design with the math library and the
build of the platform, so on Windows and Linux arm64 about 30 to 40 cases differ in the last bit (an ulp,
or an LSB after quantization). The Rust tests compare with the committed files on every platform and are
not affected; only a regeneration on another host would change unrelated cases. Making those cases
independent of the platform (own scalar math, as `sdrk_golden/scalar_math.py` already does for some cases)
is planned (see `docs/milestones/BACKLOG.md`).

The filter cases of M23 follow this rule (D107): their float expected values are exact sums (`scalar_math.fir_exact`), because the BLAS kernels behind `scipy.signal.lfilter` and `np.convolve` add in a CPU-dependent order. Check a new filter case with `OPENBLAS_CORETYPE=Nehalem python tests/golden/generate.py --kernel <name> --check` as well.

## Commands

```sh
python tests/golden/generate.py                # generate every case into tests/golden/vectors
python tests/golden/generate.py --kernel scale # only the cases of one kernel
python tests/golden/generate.py --list         # kernel/case lines
python tests/golden/generate.py --check        # compare byte for byte with the committed files
python tests/golden/generate.py --out DIR      # use another output directory
python tests/golden/generate.py --emit rds_reference --emit-out PATH [--seconds 8] [--snr 30]
                                               # write the long RDS reference signal (M41), not a case
```

`--check` prints every missing, differing or stale file (a committed file without a registered case) and
exits with 1 on any difference. The script runs from any working directory. Before generating, the Q15 model
runs a self-test of the R7 spot values, and so does the float32 model (below).

## Format (version 1)

`<kernel>/<case>.json` plus one `<case>.<array>.bin` per array. The JSON is written with sorted keys and
2-space indent. The fields are `format_version`, `kernel`, `case`, `seed`, `params`, `arrays`
(`file`, `dtype`, `len`), `tolerance`, `notes` and `provenance`. Binary arrays are raw little-endian without a
header. Dtypes: `u8`, `i8`, `i16`, `i32`, `f32`, `f64`, `ci16` (interleaved re, im), `cf32`, `cf64`. `len`
counts elements (a complex sample counts once). Tolerance classes:

- `{"class": "bit_exact"}`: raw bits are equal.
- `{"class": "tolerance", "snr_db_min": x, "skip": n}` with optional `"max_abs_err"` and optional `"snr_db_guard"`, the
  regression guard of the accuracy policy (the lowest measured SNR minus 1 dB), checked like `snr_db_min`.
- `{"class": "max_abs_err", "max_abs_err": x, "skip": n}` with optional `"min_ref_db"` and then required
  `"ref_unit": "db" | "linear"`; only samples whose reference is at or above the level are checked.

SNR is `10 log10(sum |ref|^2 / sum |ref - out|^2)` over samples `skip..`. A case stays at or below 512 KiB, all
vectors together at or below 16 MiB; the generator fails otherwise.

## Adding a case

1. Copy the template of `sdrk_golden/cases/scale.py` into a module of the kernel (new modules are imported in
   `sdrk_golden/cases/__init__.py`).
2. Choose a new seed. The `rng` argument is the only source of randomness; the draw order is part of the case.
3. Quantize the inputs yourself (`astype(np.complex64)` or `q15.from_float`) and compute `expected` from the
   quantized input, so that only kernel error is measured. Tolerance cases store `f64`/`cf64` (exception:
   `agc/steps_c32_24000` stores the f64 model rounded once to `cf32`, because a `cf64` file would exceed
   512 KiB); bit-exact cases store the exact output dtype.
4. Pick the tolerance class from the contract table in `docs/kernels.md`.
5. Run `python tests/golden/generate.py --kernel <name>`, then `--check`.
6. Commit the vectors together with the code and the Rust test that loads them.

In Rust: `let case = sdrk_testkit::golden::load("scale", "c32_random_4096")?;`, run the kernel, then
`golden::assert_matches(&case, case.array("expected")?, &actual)?`. The environment variable
`SDRK_GOLDEN_DIR` overrides the vector directory.

## The exact float32 model

Kernels whose output depends on a discrete decision (the gate of `squelch`) cannot be compared with an f64
reference, because the decision may flip one sample earlier or later. Their arithmetic is fixed by the
specification and `sdrk_golden/f32model.py` evaluates it with NumPy `float32` scalars, one operation at a time
(`add`, `sub`, `mul`, `flush_denormal`, `is_finite`); NumPy rounds every scalar operation to float32 and never
fuses a multiply with an add, so the model equals Rust `f32` code compiled without FMA. Such a case is
`bit_exact` and its JSON carries `"model": "float32"` at the top level. `f32model.self_test()` checks the
helpers against hand-computed values (for example that `0.1f + 0.2f == 0.3f` and that a product and a subtraction
are not fused) and runs in front of every generate and check run.

## The stereo cases (seeds 438 to 443 and 454)

`stereo_pll` (seeds 438 to 441 and 454) and `stereo_matrix` (442, 443) follow the model rule above: `sdrk_golden/cases/stereo.py` builds the cosine tables of `rotate` itself (`float32(cos(2 pi k / 4096))` with `scalar_math.cos`, the Q15 rule from the same f64 values) and stores their SHA-256 in every `stereo_pll` case, so a Rust test fails with a clear message when `sdrk-core` has other tables. The coefficients are stored as IEEE bits (`kp_bits`, ...). Besides the bit-exact model, every `lock_*` and `fade_*` case stores `snr_db_guard`, the regression guard of decision D111: the SNR of the difference channel (from sample `guard_skip`) of the model against the same loop in float64 with exact sine and cosine, minus 1 dB, rounded down to 0.1 dB. The float64 output is not committed (it depends on the libm of the host); the Rust test runs its own float64 loop on the stored inputs. Everything that feeds a committed byte uses plain Python arithmetic, `scalar_math` and the float32 helpers (no BLAS, no SIMD transcendental), so the files are identical on every CPU.

## The preemph_limit cases (seeds 444 to 449; `clamp_f32_4096` has no random input, seed 0)

`preemph_limit` follows the model rule above: `sdrk_golden/cases/preemph_limit.py` implements the float32 model of the `f32` variant with the `f32model` helpers and the integer model of the `Q15` variant with Python integers (no NumPy arithmetic, no `sin`/`exp`/`lfilter`; the tone bursts use `math.sin`), so the files are identical on every CPU. The cases are `preemph_f32_8192` (444, limiter idle), `limit_f32_8192` (445, limit 0.5 with two tone bursts above the limit), `limit_q15_8192` (446, the input of 445 quantized), `preemph_q15_8192` (447, tau 530 us), `nonfinite_f32_4096` (448, NaN and infinities at 20 listed positions) `retune_f32_8192` (449, `set_limit(0.5)` before sample 4096) and `clamp_f32_4096` (seed 0, 24 finite values beyond the input limit 1024, which the model clamps). The coefficients are stored as IEEE bits (`b0_bits`, `b1_bits`, `a1_bits`) and the Rust tests build the state from them. The generator asserts that the limiter visits the states the case is meant to cover. The design cases `design/preemphasis_*` (seed 0) store the values of the formulas of `sdrk_golden/design.py:preemphasis_coefs` in plain `math` floats; the generator asserts that `scipy.signal.bilinear` agrees within 1e-12.

## The M33 cases (seeds 471 to 475)

## The M35 cases (seeds 480 to 482)

`am_mod` (480) follows the model rule above: `sdrk_golden/cases/am_mod.py` implements the float32 model of the `C32` modulator with the `f32model` helpers (`x' = clamp(x, -1, 1)` with NaN giving 0, `t = depth x'`, `u = 1 + t`, `re = carrier u`, `im = +0`) and the integer model of the `CQ15` modulator with Python integers (`c_q`, `m_q` = `floor(v 32768 + 0.5)` of the `f32` parameters limited to 32767, `t = round_shift(m_q x, 15)`, `u = 32768 + t`, `re = sat16(round_shift(c_q u, 15))`). The cases are `c32_4096` and `cq15_4096`: at 48 kHz a 1 kHz tone 0.7 (`math.cos` of an exactly reduced phase) plus real noise of sigma 0.2, then 32 values beyond +-1 (`+-inf`, `+-f32::MAX`, `+-(1 + 2^-23)` and 26 random magnitudes in (1, 4)) and 8 NaN at random positions, listed in `beyond_positions` and `nan_positions`; carrier 0.5, depth 0.8. The `CQ15` case quantizes the same signal (the values beyond +-1 saturate, NaN gives 0) and stores the gains `carrier_q` and `depth_q`. Both are `bit_exact`, the `C32` case carries `"model": "float32"`.

`blocks/ssb_mod_usb_c32`, `blocks/ssb_mod_lsb_c32` (481) and `blocks/ssb_mod_usb_cq15` (482) live in `sdrk_golden/cases/ssb_mod.py`: 8192 samples at 48 kHz of two real cosine tones from phase 0 (700 Hz 0.3 and 1900 Hz 0.2), the block's defaults (band 300 to 3000 Hz, transition 200 Hz, 60 dB, `max_taps` 1023: 873 taps). The chain is the one of `ssb_demod` mirrored (helpers of `cases/blocks.py`): NCO 1 at `-s c` (`c` = 1650 Hz), the complex low-pass with cutoff 1350 Hz whose `design.lowpass` taps are multiplied by 2 before the rounding (to `f32`, or to Q15 with `round(2 h 32768)`), NCO 2 at `+s c`, with `s = +1` for USB and `-1` for LSB (both oscillators flip with the sideband, decision D431). The `C32` cases compute it in float64 (`exp` of the exact modular 32-bit phases, `upfirdn(h, ., 1, 1)` restricted to `n` outputs, `tolerance` with 90 dB); the `CQ15` case is the integer chain (the rotate table model and the integer convolution with one rounding and saturation per output, `bit_exact`). The params store `taps`, `delay` (`(taps - 1) / 2`), `tap_gain` 2 and the phase increments `inc_1` and `inc_2`. The generator asserts that every tone comes out at `+s f` with its amplitude (within 1 %) and that the mirror at `-s f` is more than 50 dB lower. 8192 samples instead of 4096, because the filter has 873 taps.

## The M38 cases (seeds 490 to 492)

## The M39 cases (seeds 530 and 531; `design/gaussian_bt0p5_sps8_span4` has no random input, seed 0)

`design/gaussian_bt0p5_sps8_span4` stores the Gaussian pulse of GFSK (`bt` 0.5, `sps` 8, `span` 4, 33 taps, `max_abs_err` 1e-12) from `sdrk_golden.design.gaussian`, which follows the arithmetic of the Rust design one value at a time (`a = 2 pi pi bt bt / ln 2`, `math.exp` per tap, the unscaled taps summed in ascending order, each divided by the sum), so no NumPy `exp` or `sum` feeds the file. `sdrk_golden/cases/fsk.py` holds the two block cases. `blocks/fsk_mod_gfsk_c32` (530) is GMSK from 1024 random soft bits `+-1` at 9600 bit/s (levels 2, `sps` 8, `bt` 0.5, `span` 4, deviation 2400 Hz): the float64 chain maps the bits to `+-1`, shapes them with `upfirdn(h, levels, 8, 1)` (8 outputs per bit), where `h` is the pulse of the block (the boxcar of 8 ones convolved with the Gaussian, scaled to sum 8 in float64 and rounded once to float32, stored as `taps`), and then integrates the phase of `fm_mod` (`floor(x k + 0.5)` modulo 2^32, `k = 2400 / 76800 2^32`) and evaluates `exp(j 2 pi phase / 2^32)` with `math.cos` and `math.sin`; `tolerance` 90 dB. `blocks/fsk_demod_2fsk_f32` (531) is continuous-phase 2-FSK (h = 1, rectangular frequency pulses) at 48 kHz and 4700 Bd (`sps` 480 / 47), with 50 ppm clock drift (D540), a random symbol offset and complex noise for Eb/N0 20 dB, the phase computed per sample with `math.cos` and `math.sin`; the chain is the float64 discriminator `atan2` of `x[n] conj(x[n - 1])` (`x[-1] = 0`) times the float32 gain `fs / (2 pi deviation)`, the boxcar of 10 float32 taps `1 / 10` summed in plain Python, the result rounded once to float32, and then the float32 model of `symbol_sync` of the M38 cases (Gardner, the block defaults, the gains of D565 with `ted_gain` 1.48, the `TED_GAIN_2FSK` of `fsk_demod`); `tolerance` 80 dB against the soft bits of the block (the symbol values), because `quad_demod` and `resample_real` are tolerance kernels. The Rust test (`golden_m39`) runs both blocks whole and in 20 chunk plans of input and output sizes; every chunked run must equal the whole run bit for bit.

## The M40.1 cases (seed 560; `blocks/slice_8psk_c32` has no random input, seed 0)

`costas/8psk_lock_c32_8192` (560) extends the model of the M40 cases to order 8 (decisions D640, D641, D659): the detector takes the 8PSK point `d` of the half-open octant `[k pi / 4, (k + 1) pi / 4)` of `y` (the quadrant from the signs, `re > 0, im >= 0` / `re <= 0, im > 0` / `re < 0, im <= 0` / `re >= 0, im < 0`, the octant from `|re| > |im|` or `|im| > |re|`; zero and NaN take point 0), the parts `+-cos(pi / 8)` and `+-sin(pi / 8)` rounded once to float32, the error `e = y.im dr - y.re di` and the lock metric `cos(8 err)`, computed as `((8 w) (w - 1)) + 1` with `w = u u`, `u = ((r r) / p) 2 - 1` and `r = y.re dr + y.im di` (the Chebyshev polynomial `T4` of the formula of M40.1 section 1, the maintainer's decision D659; the case was regenerated with it, its input and output samples are unchanged, the lock flags and the final lock level differ). The signal is 8PSK `exp(j (2 pi k / 8 + pi / 8))` with `k` from the Gray code `b0 4 + b1 2 + b2` of section 1, one sample per symbol, a random start phase and complex noise for Eb/N0 14 dB (`sigma^2 = 1 / (6 Eb/N0)`), with the defaults of D604. The float64 guard loop uses the octant rule on its float64 values and the exact float64 points. The Rust test (`golden_m40`) runs it like the M40 cases with 20 chunk plans of seed 564.

`blocks/slice_8psk_c32` (`sdrk_golden/cases/psk.py`, seed 0) holds the max-log soft bits of the `slice` constellation `8psk` (D642) for the inputs `exp(j k pi / 8)`, `k = 0 .. 15`, at amplitude 1 and 0.5 (even `k` the 8 decision boundaries, odd `k` the 8 points), `scale` 2.5: per bit `scale ((m0 - m1) * 0.25)` with the minima of the squared distances to the float32 points over the points whose Gray bit is 0 and 1, in index order with a strict comparison, exact float32 model, bit-exact; run by `sdrk-testkit/tests/golden_m40_1.rs` whole and one symbol per call.

## The M41 case (seed 570) and the long RDS reference signal

`rds/reference_short` (`sdrk_golden/cases/rds.py`, seed 570; the case itself draws no random numbers, it has no noise) holds the RDS reference signal of M41 section 5, an independent NumPy model of an RDS modulator after IEC 62106 whose steps the module docstring fixes (decisions D663 to D666): the carousel of 32 groups (PI `0xD123`, PTY 10, TP 0, alternately 0A with PS `SDRK TST` and block C `0xE0E0`, and 2A with the radiotext `Hello from sdrk!`, a carriage return and spaces to 64 characters), the checkwords (remainder of `info(x) x^10` modulo `0x5B9` plus the offset word), the differential coding `t_k = t_{k-1} xor d_k` from `t_{-1} = 0`, the biphase pulse `p(x) = h(x + 1/4) - h(x - 1/4)` with `h(x) = 8 cos(4 pi x) / (pi (1 - 64 x^2))` (`x = t / Tb`, `h(+-1/8) = 2`) cut to `-2 <= x < 2` and normalized to its largest magnitude on the 240 kHz grid `x = n / 3840`, bit `k` centred at `k Tb`, the multiplex `0.45 (L + R) + 0.45 (L - R) sin(2 phi) + 0.1 sin(phi) + 0.04 b sin(3 phi)` at 240 kHz (`L` 1 kHz, `R` 2 kHz, pilot 19 kHz) and FM with 75 kHz per unit, the multiplex held for two samples and the phase accumulated at 480 kHz, amplitude 0.5, rounded to `cs16` with the R7 rule. Every sine and cosine is the scalar `math` function at an exactly reduced integer argument (tables of `cos(2 pi r / 3840)` and `sin(2 pi r / 240)`) or of the accumulated FM phase, so the files are identical on every CPU. Arrays: `blocks` and `checkwords` (`i32`, 4 per group), `data_bits` and `tx_bits` (`u8`, 3328 bits before and after the differential coding), `baseband` and `mpx` (`f32`, samples 0 to 4095 at 240 kHz), `baseband_late` and `mpx_late` (`f32`, 2048 samples from `late_start` 1000003, in the second carousel period, where the odd parity of a period inverts the transmitted bits) and `rf` (`ci16`, samples 0 to 8191 at 480 kHz without noise); 92 kB in all. The integer arrays are exact, the float arrays carry `max_abs_err` 1e-6 and `rf` at most `rf_max_lsb` 1 LSB (`libm` against the C library); `pulse_peak` is the grid peak before normalization.

The long signal of the end-to-end tests (6 s and more) is not committed (8 s are 15 MB): `generate.py --emit rds_reference --emit-out PATH` writes it as raw `cs16` at 480 kHz with complex noise of `default_rng(570)` for `--snr` dB per sample over 480 kHz (`sigma^2 = 0.25 / (2 10^(snr / 10))`, default 30 dB, `--seconds` default 8) plus the sidecar `PATH.json`. The Rust tests do not call Python: `sdrk_testkit::rds::RdsReference` follows `rds.py` operation for operation and is checked against this case by `sdrk-testkit/tests/golden_m41.rs` (decision D663); the ignored test `python_reference_file_matches_the_model` of that file compares an emitted file with the model when `SDRK_RDS_REFERENCE` names it (the difference must be the noise of the stated SNR within 0.1 dB), and the ignored test `python_reference_file_through_the_flow` of `crates/pipeline/sdrk-pipeline/tests/fm_rds.rs` runs the same file through the flow `fm_rds_receiver` (PS, RT and at least 99 % `CRC_OK` groups after the first second, as E2E-RDS).

## The M39.1 cases (seeds 542, 544 and 545)

`sdrk_golden/cases/flows.py` holds the reference signals of the example flows in the directory `flows` (they are inputs of whole flows, not of a kernel; the tolerance class `bit_exact` stands for the exact frames the flow must give). `flows/aprs_bell202_20_frames` (542) is a Bell 202 AFSK signal at 48 kHz with 20 AX.25 UI frames for `aprs_receiver` (Test 3), made independently of the Rust modulator and encoder: an HDLC model of its own (flags, bit stuffing, LSB first, the CRC-16/X-25 of `cases/proto.py` low byte first), NRZI and a continuous-phase tone generator with `math.sin` per sample; each frame has its own preamble (4 to 12 flags), tail (1 to 3 flags), bit-rate error (up to 200 ppm), tone error (up to 0.5 %), twist (-3 to +3 dB), amplitude (0.25 to 0.6) and start phase, with 20 to 60 ms of silence after it and noise of sigma 0.01 on everything; the audio is stored as `i8` (value / 128) to stay within 512 KiB (D695), `frames` and `lengths` hold the frames without FCS. `flows/adsb_df17_200_frames` (544) is 150000 `cu8` samples at 2 MHz with 200 DF 17 frames at random positions (at least 256 samples apart), 10 to 30 dB above the noise (`A^2 / (2 sigma^2)`, uniform in dB), random carrier phases and offsets up to 100 kHz, and 40 noise bursts of 32 to 1024 samples 0 to 12 dB above the noise; `params.frames` lists each frame's index, bytes, address, level and effective SNR (over the noise plus the strongest burst overlapping `p - 256 .. p + 240`, D696). `flows/adsb_short_frames` (545) holds, at 20 to 30 dB in 24000 samples, 6 DF 17 frames and one DF 11 frame with residue 0 whose addresses fill the ICAO address cache of `adsb_decode`, then 20 short frames (DF 4, 5 and 11, parity overlaid with one of these addresses) and 4 short frames with an address not seen before; `params.frames` gives each frame's expected output (`crc_ok`, `address_parity` or `dropped`, D704). The samples are computed one value at a time with `math`; NumPy only draws the integers, uniform and normal values. The flow tests that load them are `sdrk-pipeline/tests/aprs_flows.rs` and `adsb_flows.rs`.
